# vego roadmap

What is planned and not built, and the decisions behind what is built. `docs/verification.md` describes what exists today for someone using it, and the README gives a short overview. This file is for someone changing the verifier.

## Target

vego is meant for use on real projects, not only textbook algorithms. The first target is the code found in services, command-line tools, infrastructure, parsers, and data structures: logic over integers, strings used as tokens, slices, structs, and errors, calling into the standard library and third-party modules.

Not a target: numerical, scientific, graphics, and machine-learning code, where floating point is the core logic, and code whose point is formatting or parsing text exactly.

Design choices should be judged against the first group. A feature that only helps the second can wait.

## Go that stops a function from being verified

Each of these makes vego report the function that uses it as `cannot verify`. They are listed here in one place, in the order they are meant to be built, which is roughly how often ordinary code runs into them. The sections by area further down say more about some of them.

1. **Interfaces whose methods write behind the receiver** (interfaces, third part): footprints, the memory a value owns, which a call through an interface forgets and from which callers are kept separate, and converting a value whose method writes behind its receiver, or a value of the project to an interface whose contracts speak of a state (a closer of the project to `io.Closer`, refused since state of interface values), as `*bytes.Buffer` or a writer of the project to `io.Writer`, a `Store` with `Put`, `sort.Interface` and `sort.Sort(byAge(people))`. It also lifts the cost of interfaces recorded in Interfaces: an implementation whose receiver has an invariant, or whose `Requires` reads receiver memory, cannot be converted today. And it is where a struct invariant can say that a struct owns the array of its slice, absorbing `fresh(s.items) Or within(...)`, and cover what a pointer field points to. Calls through `io.Writer` and the other interfaces of other modules are built (see Interfaces, second part), and so are states of interface values from code that is not verified (see State that a value owns, second part). Waits for nothing.
2. **Dynamic types** (interfaces, fourth part): type assertions, type switches, `==` on interface values, and typed errors (`errors.As`, a type switch on an error, what an error of a struct type holds, a struct error type converted to `error` as a third known origin). Constraints recorded in Interfaces bind it: an assertion to an interface whose contracts are not declarations in the static type's method set stays `cannot verify` unless the assertion checks them, and the tags of dynamic types follow `types.Identical`. The helpers that decide what can hold code a call may run (`holdsContractedValue`, `holdsCallable`) must then count every interface, errors included. Waits for nothing, but is more useful after the third part. An assertion must keep the reference of the value, as a conversion between interfaces does, so that the result has the states of what it holds (see State that a value owns, second part).
3. **The rest that waits on interfaces** (fifth part): `recover`, which returns `any` (see Function literals for what giving it a meaning would assume) and needs dynamic types; `defer cancel()` after `context.WithCancel`, which needs an entry for a trusted function that keeps a value (see Function values, Not built yet); `sort.Slice`, which needs `any`, dynamic types, and a contract under `calls` that can demand that `less` is an order (see Callbacks handed to trusted functions); and implementations that call through interface values (decorators, a `Writer` wrapping a `Writer`), which need a termination argument across values, such as a depth at which values are made, and that needs the wrapped field to be immutable, which footprints can give.
4. **Calls to variadic functions**, which `log.Printf` and `fmt.Println` are, and `append(s, t...)`.
5. **Arrays**, and with them every struct that holds one.
6. **Package-level variables** other than error sentinels. Existing code is full of them, and a function that reads one cannot be verified at all today. When they come, a contract that names one reads memory, which the rule for a call beside an `append` depends on (see Order of evaluation). So does a package-level variable of function type, which code during initialisation could call.
7. **`copy`, comparing structs with `==`, labelled `break` and `continue`, `goto`, `fallthrough`, `select`, `defer` inside a loop (one inside a function literal that the loop calls is built), a `range` over a map that changes a map of that type, a call with several results as the arguments of another call (`g(f())`), an `append` inside a larger expression, and a call in the target of an assignment beside an `append` that may write in place, unless the call modifies nothing and its signature refers to no memory.**
8. **Pointers to anything but a struct**, such as `*int`.
9. **Generic functions and types.**
10. **Goroutines and channels.** A proof is about one goroutine; nothing is said about what runs beside it.

Function values of named types with a contract are built (see Function values), and so are functions handed to a trusted function that calls them while it runs (see Callbacks handed to trusted functions), and interface values whose methods have contracts and write nothing behind their receiver (see Interfaces), and contracts in the trust file for methods of interfaces and for function types of other modules, five of which ship (see Interfaces, second part), and states of interface values from code that is not verified, with `(io.Closer).Close` (see State that a value owns, second part). Three parts of function values were left out and are listed under Function values, each as a feature of its own: a literal used as a value whose contract has to speak of what it captures, a value that calls a value, and a contract for an unnamed function type at the place it is used.

Two things do not stop a function from being verified but come up as often:

- **Conversions that drop bits and arithmetic that wraps**, as in `byte(x)` and a hash, are errors by design. `byte(x & 0xFF)` verifies. A way to say "this wraps on purpose" at one operation is not planned yet and would have to be loud.
- **Contracts for the standard library.** Only a handful of functions have shipped contracts, of the methods of concrete types only those of `sync.Mutex` and `sync.RWMutex` that lock and unlock (see State that a value owns), and five of the methods of interfaces and function types: `(io.Writer).Write`, `(io.Reader).Read`, `(io.Closer).Close`, `(context.Context).Err`, and `context.CancelFunc`.

## The annotation language

Settled on 2026-11-16, after trying whether formulas could be Go expressions parsed by `go/parser`. They could, for the most part, but implication and quantifiers have no Go spelling and came out worse, and `go/types` rejects formulas that mix integer types, which mathematical integers allow. The language stays its own, which also leaves room for forms that Go syntax would make awkward.

- **One spelling for each thing.** An annotation is `// @Keyword ...`, with one space after the slashes and none after the `@`, which `gofmt` leaves alone (it turns `//@Keyword` into this form inside doc comments); `// @ ...` continues the annotation above it; any other spacing is an error. Length is `|A|`; there is no `len`. `Ensures` stands in the doc comment and nowhere else. `Variant` serves loops and, in a doc comment, recursion; `Measure` is gone.
- **No annotation is skipped quietly.** A comment that looks like an annotation and is not read as one is an error: a keyword that is misspelt, glued to its formula, behind another spacing or behind other text, an `Ensures` outside a doc comment, and an ordinary comment line directly after an annotation, which may have been meant as its continuation. A comment after an annotation needs an empty `//` line before it. Since the keyword follows the `@` directly, a wrong keyword looks like the tag of another tool, as in `// @Post` and `// @Summary`. So every unknown word there is an error, and a project that has such tags declares them with `-vego.other-tags`; guessing by how close a word is to a keyword let `// @Post r > 100` pass without the clause. The rule holds wherever an `@` starts a line but for signs, block comments included. Behind other words, as in `// note: @Post ...`, only a keyword or a word within two letters of one is reported, since an address or a handle looks the same; that is the limit. A package in which collecting the annotations drew any report hands none of its contracts or invariants to other packages, since an annotation that was not read, or was dropped or misplaced, may have been meant for any of its functions; the rule is tied to the collecting step as a whole, so a report added there later is covered without being remembered. One thing is let through on purpose: an annotation behind slashes of its own, as in `// // @Ensures ...`, which is one commented out or shown in an example. The scanner compares letters, so a keyword spelt with letters of another alphabet that look the same is not recognised.
- **A verified function names its results.** A contract refers to results by name, and Go does not let a result share a name with a parameter, so a name in a contract cannot mean both. `True`, `False`, and `nil` stay reserved for the formula language. `result` and `result1`, `result2` remain only for trusted functions that leave their results unnamed.
- **Unchanged:** `And`, `Or`, `~`, `->`, `<->`; `=` for equality; the prime for the state on return and `old` inside bodies; intervals such as `[0, n)`.
- **An `Ensures` speaks of the return through results, primes, or `fresh`** (built with state of interface values, at the orchestrator's request). A top-level conjunct of an `Ensures` that has none of these is a fact about the state at the call, which the `Requires` must give anyway; when it reads memory the function may modify, its author most likely meant the value on return, as in `@Ensures p.x = 7` on a function that sets `p.x`, which verified whenever the `Requires` said so. Such a conjunct is refused, with a message that shows the primed path (`entryonly.go`). Whether it reads such memory is decided by proof: its value on entry and its value after every target of the frame is forgotten must be proved equal, so a read through a predicate, recursive or not, a quantifier, `has`, a length, or a state counts, and so does one that may alias a target; an inconclusive proof refuses. It applies to verified functions, contracts of function types and interface methods, and trust entries. A clause relating a result to the entry state, `r = p.x`, is kept. In the corpus and the guide it found one clause, `defects/defects.go` `EntryVersusExit`, written to show exactly this mistake.
- **Two more keywords**, `State` on an interface type and `Receiver` on a method of one (see State that a value owns, second part).
- **Missing, from the first readers of the guide:** character literals, `cap`, comparing a slice with `nil`, a way to say that two slices share no memory, and `fresh(s.items)` being written without the prime although it speaks of the state on return.

- **Speed.** Measured with speed on 2026-11-19 (F11), on a machine with 24 cores and 31 GB, other agents idle, load average about 1. What was built is recorded under The prover (the cache of answers, what each answer costs, `-vego.cost`, the guard of the corpus costs) and under Errors (the always-fails check asks only what is read, the question whether no state forces success only for a reported contract, the order of the questions). What is known and not fixed:

  - **Deep type facts in the questions after a call** (found with speed; solved with F12, which found that the facts were not the cost: see Problems in which a region holds sequences are solved without extensionality, under The prover). In `slowhttp`, every slow question is one whose answer is open when Z3 finds no model: the contradiction check of the trust entry of `get`, `canReach`'s contradiction check after the call, the proof that the error is nil after the call, and the proposals and accepting proofs of the input search, for `get`'s contract and for the path after the call. They carry the type facts of what the call returns, which `deepFacts` and `contentFacts` (`calls.go`) state for the results and the arguments of a call (`involved` in `call`) and for the inputs of the always-fails check (`errors.go`, `contractInstance` and `forcesSuccess`): every byte of `Status` and `Proto` in 0..255, every value of `Header` and `Trailer` for every key a slice whose bytes are bytes, every string of `TransferEncoding`. These are universally quantified facts over nested arrays (`SeqSeqSeqInt`). Each question runs to the limit at 0.3 M units a second, against 1.6 M on average in the corpus: in one, 36,721 array extensionality axioms and 3,431 final checks. The state itself states type facts only at reads, so only these questions carry them. Seven of the problems, at 35dca07, were in `testdata/slow` until F12 removed it (they are at befc067), each with a first line that says what asked it and what it cost (two of them were asked twice; the cache now answers the second). What removing facts did, with the pinned Z3: without any quantified fact every one is sat within 9,000 units in 0.02 s; keeping only the facts about bytes, the trust entry's check (`trust-entry-contradiction.smt2`) is still open at the 4 M limit, and sat at 8.4 M; without only the facts about map values, it and the two others tried (`reach-contradiction.smt2`, `accept-sample.smt2`) are still open at the limit, in 0.6 s instead of 11 to 19 s; with every fact, at ten times the limit, the trust entry's check gives up after 23 M units with "incomplete quantifiers". So no limit finds a model, and the facts about map values are what make each unit slow. `slowresp` reproduces the cost without `net/http`, an interface, or a pointer field: a trusted function returning a struct with the fields of `http.Response` that hold strings, slices of strings, maps of them, integers, and booleans took 84 s for `Code`, with 31 s more for the entry, as the reviewer measured it; one `map[string][]string` alone in a struct took 3.1 s.
  - **A proof obligation that fails costs its whole limit**: 4 M units, 1 to 4 s in the corpus and up to 18 s in `slowhttp`. That is what `-vego.rlimit` bounds.
  - **Long functions cost the square of their length.** Every obligation carries every fact so far: the 1,300th problem of the 120-statement function is 102 KB with 1,403 assertions, and the function sends 75 MB in all. `ctx-simplify` took 550 k of the 607 k units of such a problem, and encoding is 65% of Go's CPU there (4.8 s of 7.4 s). Since F12 the chain has no `ctx-simplify`. The program of the table and of these figures is not in the repository. Another of the same description, `testdata/src/straightline` (887 problems, 27 MB of text, not part of the tests), went from 42.4 M to 19.2 M units and from 50 questions that stopped at a limit to 2, but its time stayed at about 9 s, since encoding and reading the text are what grow with the square. Encoding a shared prefix of hypotheses once was left out (decided by the orchestrator): whether a term becomes a `define-fun` depends on its uses in the whole problem, so the text of a prefix depends on what follows it. Sending fewer hypotheses would lose proofs, and where a failed proof is the quiet outcome it would make vego quieter: a Modifies entry would count as needed, `dependsOn` would report a dependence, `canReach` would report a path as possible, and the contradiction checks after calls and of entries would report nothing. That breaks the loudest-path rule, so it was not done.
  - **One field written through twenty-four or more pointers is not proved at the default limit**; see The prover. With ten to twenty-three it is since F12, which took `ctx-simplify` out of the chain.
  - **Each problem costs Z3 about 1.2 ms to build its context after `(reset)`** (the first command after it builds the AST manager; `(reset)` alone takes 0.02 ms), about 12% of Z3's time on the corpus. Starting the context early with `(reset)(push 1)(pop 1)`, while Go builds the next problem, was tried and dropped: it adds 8 units to Z3's count on 148 of 150 problems drawn from the corpus, and on one (a problem of `callbacks.countdown`) the search itself changes, 4,700 units and 25 decisions against 7,536 and 36. Since the count is what the limit bounds, it could change an answer. To try it on another Z3, compare `(get-info :all-statistics)` of every distinct corpus problem with and without it, leaving out time and memory.
  - **The functions of one package are verified one after another** (a later feature, decided by the orchestrator, with a design of its own, since the last time a result depended on an order it was a soundness hole). In a run of one package three of the four Z3 processes are idle: the guide's 2,120 questions go through one queue. A package of several slow functions could gain up to four times; one slow function, as in `slowhttp`, nothing.
  - **The other tests of the vego package run one after another**, about 27 s (TestBitFacts 9 s, TestTypeEntriesInUse 6 s, TestCopiesConfirmed 6 s, TestFormatWraps 5 s).
- **What the first readers of the guide could not do.** Two reviewers tried to verify small realistic programs with only `docs/verification.md`. A new module went well; a service with a mutex, a map of structs, wrapped errors, an interface, and a global did not. What stopped them, beyond the list above: formulas have no character literals, no `cap`, no way to compare a slice with `nil`, and no way to say that two slices share no memory (`within` rules out only that one lies inside the other); `fresh(s.items)` is written without the prime although it speaks of the state on return; a sum or count over a slice that is being written cannot be carried through a loop; an invariant of a struct type is not known of the elements of a slice.
- **Continuous integration.** The tests, including those of the shipped contracts, run by hand and on one toolchain. 32-bit targets have only been tried in a few spots.

## By area: what is built, why, and what is missing

### The prover

Built: obligations are discharged by Z3, run as a separate program and fed SMT-LIB text (`vego/internal/solver`). It replaced a prover written in Go on 2026-11-17. The old one was deliberately incomplete in ways that kept showing up as work for the user: no model of a failing goal, a fixed depth of instantiation and unfolding, and a step budget that ran out on true goals.

Decisions:

- **One pinned version.** `solver.Version` names the release a version of `laas` uses (5.4.1), and any other is refused with a message saying how to install it. Another version may prove different things, and a proof that comes and goes with the installed Z3 is not a result. Moving to a new release is a change of its own, run against the whole corpus. Z3 is looked up only for a package that has something to prove.
- **A binary, not bindings.** No cgo. The protocol is SMT-LIB on standard input, one problem at a time, each preceded by `(reset)` and followed by an `echo` marker; any reply other than `sat`, `unsat`, or `unknown` with its reason is a fault of the run, never a proof. The output is read while the problem is written, since Z3 prints an error for each bad command. Up to four processes are kept per run, each limited to 1 GB; a process that ran out of resources is replaced.
- **Deterministic effort.** Each problem has an `rlimit`, which Z3 counts the same way on every run of one binary. Z3's default tactic tries some solvers for a fixed time before others, so problems are solved with an explicit chain of simplifications and the core solver, which has no timed step (see The chain has no `ctx-simplify`). A wall-clock limit of five minutes is only a backstop and is reported as such. Seeds are fixed on the command line, since options set in a problem survive `(reset)`.
- **An answer is kept by the text of its problem** (decided with speed, by the orchestrator). A `Solver`, one per binary, keeps in its process, never on disk, what Z3 answered to each problem: the status, the reason, the values asked for, and the resources counted, under a key of the whole SMT-LIB text and the names whose values were asked. A problem asked again is answered from there. This rests on the decision above: after `(reset)`, with the options fixed on the command line and the limit in the text, Z3 of one binary answers a text the same way every time, which is already what lets any of the four processes serve any problem. What depends on the machine is never kept: a problem past the wall limit, one out of memory, a process that died or replied with anything else, and an unknown for want of memory. An unknown because Z3 was canceled is kept: vego gives Z3 no time limit, so Z3 cancels only at the resource limit, with the same count every run (two quick questions of the guide come back `canceled` at 200,917 and 202,770 units against a limit of 200,000), which is why `exhausted` reads it as the limit. The text kept is bounded at 256 MB per process, the oldest forgotten first. Soundness does not rest on the premise: an answer is reused only for the text that produced it. The premise is what makes the messages the same with and without the cache. At 35dca07, 5,976 of the 22,309 problems of the corpus repeat a text asked before in the same run, 4,842 of them in the same package.
- **Every answer says what it cost.** Each problem ends in `(get-info :rlimit)`, and a reply without the count is a fault like any other unexpected reply. `Options.Observe` is told the result, the length of the text, the count, whether the answer came from the cache, and the time; a cached answer reports the count Z3 gave when it solved the text, so the count does not depend on which package asked first.
- **The cost of the corpus is recorded per function, and must not move unseen** (decided with speed, by the orchestrator, with the reviewer's F2). `testdata/costs.txt` records, for each function of the main corpus run of TestAnalyzer, by package and name, the problems asked of Z3, the resources Z3 counted, and the problems it left open (at a limit or unknown). A cached answer counts as Z3 counted it, Z3's count ignores the comments of a text, and the questions come in a fixed order, so the numbers are exact. With the Go version, system, architecture, and Z3 that recorded the table, any difference fails, growth and drop alike, so a change that makes verification slower is seen where it happens and one that makes it faster records the gain; with another Go version only growth of more than 10% fails, since the types of the standard library may change what is asked. A function missing from the table fails, and so does one the table lists that asked nothing, so a program is added to the table deliberately. Bytes of text are not compared: comments carry numbers that the process hands out in the order packages ask. A count of resources does not track time, which ranged from 0.3 M to 45 M units a second; the count of open problems is what catches a quick question that comes to run to the limit. `VEGO_RECORD_COSTS=1 go test ./vego -run 'TestAnalyzer/verifies'` rewrites the table.
- **`-vego.cost` tells what each function asked** (decided with speed, by the orchestrator). It prints, on standard error, per function: the problems, the resources Z3 counted, the bytes of text without comments, the seconds, and each place and kind of question that stopped at a limit (`cost.go`). It changes no result. A question counts against the function of the innermost `pv.run`, at the statement being executed or the position of the obligation, as one of five kinds: proof obligation, question of the always-fails check, contradiction check, check whether a Modifies entry is needed, quick check. A question asked while no function is being verified panics as an internal error, so a question added later cannot go uncounted. The seconds include waiting for a free Z3 process, and leave out the time of other functions a function leads to; they are the one number that moves with the machine.
- **Problems in which a region holds sequences are solved without extensionality** (F12, decided by the orchestrator, with F1 to F3 of its review). The last tactic of their chain is `(using-params smt :array.extensional false)`, written in the problem, so it is as deterministic as the rest (`tacticWithoutExtensionality` and `encode` in `solver.go`).

  Soundness does not depend on which problems are picked. Without the axiom of extensionality, by which two arrays with the same elements are equal, the theory is weaker, so a problem without a model there has none with the axiom, and every `unsat` stands, for whatever problem it is used.

  The rule that picks them is there so that no proof is lost. The logic has no equality of sequences (the encoder faults on one), and a sequence is an argument of only two kinds of uninterpreted symbol: the key function `S.key`, and a recursive predicate with a sequence parameter. Every other symbol applied to a sequence (select, store, the constant array, the lambdas of concatenation and cut, `ite`, the constructor and fields of the datatype, a quantifier, `Options.Forall` over constants of sequence sort) gives equal results for sequences with equal elements. In a model without the axiom, identifying arrays with equal elements then gives a model with it. So a problem without a key or such a predicate has a model with the axiom exactly when it has one without, and a problem with either keeps the axiom (`tellsApart`). That the two have the same models does not make Z3's answers the same (F2 of the review). Its procedure is incomplete with quantifiers, and without the axiom it may stop at a limit, or give up on the quantifiers at once, where with the axiom the new indices of its axioms led to a contradiction. That this loses nothing is measured, not proved.

  Of the problems the rule allows, only those in which a sequence of sequences of sequences is declared leave the axiom out: a region that holds strings, slices of strings, or slices held as map values, inside structs or slices. That choice comes from measurements of this corpus and is a rule to revisit, not a law. Leaving the axiom out of every problem the rule allows was measured on the 15,721 problems of one corpus run. With the old chain it made 21 problems that Z3 answers `sat` within 5 to 45 k units with the axiom run to a limit, since Z3 uses the axiom to finish a model, and 7 more reached a limit. With the chain without `ctx-simplify` it lost one proof (a problem of `manywrites`, `unsat` at 3.55 M units with the axiom), sent 22 `sat` answers to a limit, and left 23 problems at a limit in all. The narrower rule selects 73 of the corpus problems. It changes none of their answers, and the count of one goes up, a `sat` from 5,586 to 7,459 units, which `memory.CountDigits` asks twice (60,522 to 64,268 units in `testdata/costs.txt`, the only change of the table). Someone who finds a slow problem outside the selection, one whose questions after a call carry quantified facts over nested arrays without a region of strings, should measure it against the axiom before anything else.

  Where the axiom made Z3 slow: with quantified facts about what the types guarantee of contents (bytes of strings, values of maps under every key), Z3 kept adding extensionality axioms between the rows of a region, each with a fresh index whose read matched the facts, whose instances made new array terms. On the trust entry's check of `slowhttp` that was 36,721 `array-ext-ax` and 40,721 `array-splits` in 4 M units and 11 s. `smt.mbqi=false` and dropping `ctx-simplify` changed nothing there. Without the axiom it ends `unknown (incomplete quantifiers)` after 36,941 units in 0.01 s. Through vego, at befc067 against now:

  | function | problems | units | seconds |
  | --- | --- | --- | --- |
  | `slowhttp.Fetch` | 39 to 39 | 13,485,852 to 268,333 | 81.7 to 0.16 |
  | the trusted contract of `slowhttp.get` | 7 to 7 | 13,027,224 to 1,109,851 | 40.8 to 0.34 |
  | `slowresp.Code` | 27 to 27 | 13,438,828 to 263,414 | 81.4 to 0.15 |
  | the trusted contract of `slowresplib.Get` | 7 to 16 | 14,007,481 to 1,282,371 | 30.7 to 0.46 |

  The check of `Get`'s entry asks more now: its proposals get values instead of stopping at the limit, so the search offers more of them. No message changed anywhere. `slowhttp` and `slowresp` are now in the main corpus run, where the table of costs holds them to these counts.

  Guards. `TestProveIsSound` solves its random problems also without the axiom, the same problems with the same seeds: 1,127 and 1,276 are proved either way, each confirmed by evaluation (F1 of the review). `TestExtensionality` checks the rule. Two problems need the axiom, a recursive predicate and a key inside a quantifier of a sequence that a write left as it was, and each also declares a region of strings, so that only `tellsApart` keeps the axiom. Both failed on a version without that condition, at the choice of the chain and, with that check off, at the proof (F3). Other problems check reads through writes without the axiom. `testdata/src/deepfacts` holds six trust entries whose promises contradict what the types guarantee: a byte of a string, a map value, a string in a slice, a quantified promise over every byte, a byte of an argument's element, and a value of a map argument. Each is still reported. - **One field written through twenty-four or more pointers is not proved at the default limit** (found with speed, F3 and F14 of its review; measured again with F12, F4 of its review). A function that writes `p_k.x = 1` through `n` pointers and ensures `p_k.x' = 1` for each verifies with up to twenty-three pointers, and leaves postconditions not proved with more: 1 of 24, 1 of 25, 2 of 26, 4 of 27, 6 of 28, 6 of 29, 7 of 30, 15 of 35, 23 of 40, each with the note that `-vego.rlimit` raises the limit, and `-vego.rlimit=40000000` proves all thirty. The seven need 4.3 M to 10.6 M units, with the same count under every chain tried, spent on read-over-write case splits in the core solver (78 k `array-ax2`). The cause is how a region is written for Z3. A region is a sequence of rows (`SeqSeqInt`), and a write of one field is `store(T, r, store(select(T, r), a, v))`, whose inner read of the previous region needs a chain of case splits of its own. On a generated problem of thirty writes through pointers that may be equal, the count of a read after later writes is:

  | encoding of a region | after 29 later writes | after 20 | after 2 |
  | --- | --- | --- | --- |
  | a sequence of rows (as built) | more than 4 M | 3.6 M | 11 k |
  | an array of arrays without the datatype | more than 4 M | more than 4 M | 7 k |
  | a two-dimensional array `(Array Int Int Int)` | 5.9 k | 10.9 k | 5 k |

  Turning extensionality off does not change this. Through one pointer the encodings cost the same (thirty writes, about 4 k units each), so what a two-dimensional region would buy is code that writes one field of one struct type, or elements of one element type, through many references that may be the same and then reads it: a function that resets a field of many structs it is handed or reaches (`ps[0].x = 0`, `ps[1].x = 0`, ..., or `a.n = 0; b.n = 0; ...`), and one that links many nodes of one type (`n1.next = n2; n2.next = n3; ...`). Different fields are different regions, and a slice of structs is one reference, so filling a table or a struct is not this shape. It is a feature of its own (decided by the orchestrator), a redesign of the encoding of memory with the scrutiny the memory model had. A row is also a sequence value: a slice is a cut of a row (`view`), an allocation stores a filled row (`storeRow`), a havoc relates rows, predicates and quantified formulas take rows and cuts of them, and the samples of the always-fails check store rows. Each of these would need a row built from the two-dimensional array, which is a lambda unless every read is pushed through to the array, and reads through lambdas made Z3 loop before (see No lambda where a read will do). `testdata/src/manywrites` holds the thirty-pointer function, expected to verify and marked with its 7 failures (1,021 problems, 69 M units).
- **The translation keeps the meaning the logic had.** Integers and references are `Int`; floats and errors are uninterpreted sorts, with the nil error a constant and some other error not nil. Two errors are the same error when they are equal, and `errors.Is` is an uninterpreted function of two errors, `error-is`, about which only the facts the verifier adds say anything (see Errors). A sequence is a datatype of an array and a raw length: reads are total, a filled sequence holds its value everywhere, and the length is the raw length or zero where that is negative. That last rule replaced "every length is at least zero", which as an axiom would contradict a sequence built with a negative length, and which as a quantified fact kept Z3 from finding models. Go's truncating `/` and `%` are written with SMT-LIB's Euclidean ones, and division by zero is an uninterpreted function of the dividend. Every node is sort-checked before it is written, since Z3 converts between booleans and integers silently.
- **No lambda where a read will do.** A read of a cut, a fill, or a concatenation is written as the read it equals, and a predicate that does not reach itself is written out in place with its bound variables renamed. Reads through the arrays that lambdas build made Z3 match facts about a cut against every read of the whole, and loop.
- **Facts about moved indices get a copy.** Z3 matches `A[k + lo]` in a fact only against reads whose index is a sum with `lo`. For an asserted `Forall` without a quantifier inside, a read of a fixed sequence at `c*k + t` gets a copy of the fact over the index itself, triggered by every read of that sequence; in the copy that read is written `A[i]`, so an instance makes no new read. Copies for denied facts, or for nested quantifiers, cost more than they gave on the corpus.
- **Keys are related pairwise.** The key of a sequence is an uninterpreted function, and every two sequences keyed outside quantifiers get the fact that their keys are equal exactly when their contents are. A quantified axiom with a multi-pattern does the same for keys inside quantifiers, but kept Z3 from finding models; it was tried and dropped.
- **Recursive predicates are axioms.** A predicate that reaches itself is a declared function with its definition as an axiom triggered by its applications. Recursion only in positive position has a fixed point, so the axioms have a model.
- **A model is never evidence.** The translation describes more states than Go has: a map whose count disagrees with its keys, junk past the length of a sequence, a division by zero with a chosen value. So `sat` decides nothing. Where the verifier needs an input to exist, as in the always-fails check, Z3 proposes values for a sample of a simple shape and the verifier proves the facts about the sample with those values before it accepts it. `unsat` is used as evidence where it is sound to: that no state of the logic forces success means no input does, and the message then says so.
- **A write names its region once.** Writing one element of one sequence of a region is `Write(T, ref, at, v)`, which means `Store(T, ref, Store(Select(T, ref), at, v))` and holds `T` once; the encoder writes the long form with `T` shared. Written out, the old form doubled the region as a tree with every write, so 24 writes to one slice used more than 4 GB before this.
- **Every formula has a bounded size.** A term records its size as a tree, and building one larger than 2^20 nodes stops the function with `cannot verify F: a formula built to verify it has grown beyond 1048576 nodes`, so that no input uses memory without bound. Terms share structure, but printing and walking them costs their size as a tree. So no rule may put an operand into what it builds more than once: `min` and `max` on integers are a new number with their two bounds and the choice, and a signed `>>`, a substring to the end, the count of a map write, `[]byte(s)`, a bitwise operator whose `and` is an operand, and any write of something read from the region it writes name the repeated part with a constant of its own (`named`, `apart`). The test binary also checks that a value bound or stored is not more than eight times larger as a tree than its distinct nodes, so a rule that doubles fails on any corpus program that uses it twice in a row; `semantics/chains.go` repeats each of these operations thirty times.

Not built yet: a region as a two-dimensional array, so that a field written through many references that may be the same is read back cheaply (see above); starting Z3's context early, tried and dropped (see Speed); counterexamples in diagnostics, which the models make possible once the names of the logic are mapped back to Go and a model is checked against Go's states; floats through Z3's floating-point theory; and moving to new Z3 releases with a test that the corpus still verifies.

### Structs and pointers

Built: the memory model, structs as values, pointers to structs, methods, `Modifies` clauses checked in both directions, nil checks, slices that share arrays (assignment, slicing, `append` in place or moving), `fresh` and `within`, trusted contracts for methods and for functions returning pointers and slices, and contracts with `Modifies` across packages.

Decisions:

- **Sharing is reasoned about, not forbidden.** The verifier models memory as a whole. Where two pointers may refer to the same struct it considers both cases, so a contract must hold when they are equal or require that they differ.
- **Memory is a set of allocations, and a pointer is an allocation and a position in it.** Everything that Go allocates in one piece (a struct made with `&T{...}`, the array of a slice, a variable whose address is taken) is one allocation. A pointer holds which allocation it points into and where; a slice holds the allocation, the position of its first element, its length, and its capacity. Structs lie at byte offsets, as the compiler places them, so that a struct inside another struct or inside an array has a position of its own and a pointer to it is an ordinary pointer.
- **Memory is split by struct type and field, which is sound because the split follows what Go can express.** There is one region for each field of each struct type, ignoring names and tags since conversion ignores them, and one for each element type of a slice of anything but structs. A region holds, for each allocation and position, the value of that field there. Two regions never hold the same memory: without `unsafe`, the same bytes can only be seen as fields of two struct types when one converts to the other, and those share their regions. Within a region nothing is assumed apart: two pointers, or a pointer and a slice, overlap unless the facts at hand say otherwise. An earlier design gave each pointer a whole object and assumed that objects of different types never met; a converted pointer broke that, and it was replaced rather than patched.
- **A variable whose address is taken lives in memory.** The function is scanned for `&x`, `&x.f`, and calls of pointer-receiver methods on `x`; such a variable gets an allocation where it is declared, a new one each time the declaration runs, and every use of it reads or writes that allocation. The variable of a `for` loop gets a new one for each iteration, holding the value the last one ended with, as Go does from 1.22 on; in a file compiled as older Go the iterations share it, and taking the address of a `range` variable there is not supported. Other variables stay values the verifier holds itself, which is cheaper to reason about.
- **`Modifies` is declared, and checked in both directions.** A function lists what it may write, as paths from its parameters read on entry. A write to anything else that existed on entry is an error, and so is a listed entry that no write needs, so the declaration cannot drift from the body. Callers know that everything unlisted is unchanged. Whether an entry is needed is decided by a quick proof attempt for each write; when that attempt is inconclusive the entry counts as needed.
- **A slice entry covers the capacity.** `Modifies A` allows writing every element up to the capacity of `A`, because an `append` to `A` may write there. Callers lose what they knew about that stretch, and cut the capacity with `A[:n:n]` to keep the rest. A finer entry that stops at the length, for functions that never append, is possible later.
- **Slice parameters of one element type do not overlap**, capacities included: assumed on entry, proved at every call. There is no way yet for a function to say that it tolerates overlap.
- **A field of a type that is not modelled is still part of its struct.** It is a hidden part that is copied, overwritten, and forgotten with the struct, so that assigning the whole struct counts as writing it. A struct that holds an array is the exception and is not modelled at all, since a slice of the array is a second view of the struct's memory.
- **A value without size has no identity.** Two pointers to such values may or may not be equal in Go, so nothing is assumed about where they are, and annotations may compare them only with nil.
- **`defer` is a call at every return.** The function, receiver, and arguments are settled where the statement is written; at each return the results are assigned to their variables, the calls that were put off are verified last one first like calls written there, and the results are read back from their variables, since a deferred function literal may assign them. Inside a loop the number of calls is not known, so that is not supported; a `defer` belongs to its own frame, so one inside a function literal that the loop calls is.
- **Nil.** Every dereference carries a proof obligation that the pointer is not nil. The verifier generates and discharges it; the user writes `Requires p != nil` for parameters and nothing at the dereference.
- **`append` forks.** Whether an append writes in place or moves the slice is decided by the capacity, which is often unknown, so execution continues once for each outcome. That is why an append has to be a whole right-hand side or a returned value. Inside an expression it would have to be a write on condition of the capacity instead, made the way a call on the right of `&&` is (see Order of evaluation), with a header that is one of two; that is not built, since using it for every append would change the proof of every append.
- **Loops forget memory by region.** A region the loop writes, in its body, its post statement, or its condition, gets a new unknown value. If every write to it goes through a variable the loop does not assign, or through a slice the loop only appends to, everything else that existed before the loop is known to be unchanged. Otherwise only what existed on entry and is not listed in `Modifies` is known to be unchanged.
- **A loop keeps what a call keeps** (changed on 2026-11-19, with state that a value owns, decided by the orchestrator; F10 of the review). A write to one struct, or to some of its fields, is a target whose cells are known (`target.single`). A layer of a region kept unchanged only what lay outside the positions from the target's first cell to its end, in every region the struct reaches; it now keeps everything but the position of each of the target's cells in that region, which is exactly what `havoc` writes for the same target. The old rule lost the fields of a second struct whenever the model could not rule out that it lay a few bytes after the first in one allocation: two distinct `*sync.Mutex`, one locked in a loop while the other is held, and the same with `reset(q)` on a `Point`. A layer now records its region (`layer.key`). A call also roots its write at a variable when it is passed a pointer to a field of the struct the variable points to (`fieldHolder`), as `h.mu.Lock()` passes `&h.mu`; before, such a write fell back to forgetting all of `Modifies`. The corpus `layers/` has the programs that verify now and defective ones for each way the rule could keep too much: a variable the loop assigns, pointers that may be equal, a pointer into a slice of structs, a write through an element, a field written directly or by a call, a nested loop, a literal called in the loop, a state beside a field, a field behind a second pointer, and a promoted field. The model still does not know that two pointers to one struct type are equal or at least its size apart, so `p.b` may lie where `q.a` does, with or without a loop.
- **Where a pointer or slice comes from is stated with `fresh` and `within`.** A function that returns something new says `fresh(result)`; one that appends to a slice it holds says `fresh(s.items) Or within(s.items', s.items)`. Without such a clause the caller knows nothing about what the value may share.

Not built yet:

- **Checking a trusted `modifies` against source.** For a trusted function whose source is available, analyse the body and report a write the entry does not declare. This catches some wrong entries; it cannot certify one, because the analysis stops at assembly, `unsafe`, and calls through interfaces or function values. The trust report should say for each entry whether the check ran to completion.
- **A wider search for inputs.** A function that returns an error has to have a contract that some input makes succeed. That input is looked for among samples of a fixed shape: slices up to 4096 long whose elements are all alike or a literal the contract mentions, strings of one repeated byte or a literal, pointers followed two deep, and maps with one key. Z3 picks the numbers of a sample, and a proposal is accepted only once the facts about it are proved; up to 32 shapes and four proposals for each are tried. An honest contract whose only successes lie outside those shapes (elements that differ from each other, a chain of three pointers, a map with two keys) is reported, in a message that says the search found nothing, and its author has to add a clause that a simple input satisfies. When Z3 shows that no state at all forces success, the message says so instead. Shapes could be chosen by Z3 too, with one sample of symbolic shape whose choices are constants.
- **Checking that annotations mean something.** An index out of range or a division by zero inside an annotation is not an error today. The plan is the usual one: each formula gets a condition under which it is defined, read left to right through `And`, `Or`, and `->` and through the bounds of quantifiers, and that condition is proved where the formula is: a `Requires` from the clauses before it, an `Ensures` in the state on return, an invariant at the loop head.
- **Arrays.** Until they are built, a struct that holds an array is not modelled at all, because `s.arr[:]` is a slice into the struct and a hidden field would not show that writing the struct changes the slice. The plan: an array field of `N` elements of a single value occupies `N` positions in the region of its element type, starting at the field's byte offset, which cannot collide with a neighbour since every element takes at least a byte; an array of structs lies at byte offsets like a slice of structs. A cell then covers a run of positions, and an array value is a sequence, as a string is.
- **Pointers to anything but a struct**, such as `*int` or `*string`. A field of type `int` lives in the region of its struct and field, and an element of a `[]int` in the region of `int` elements, so an `*int` could point into either and would have to say which. The way to build it is to key the regions of single values by their type alone, at byte offsets, for all structs and slices; fields of different structs then share a region and are told apart by position, which costs the solver the separation it now gets for free. Worth doing once it is measured.
- **Linked structures** such as lists and trees. They can be built and read, but a loop that walks one forgets every node the function may modify, and there is no way to state an invariant over all nodes.
- **Letting a function accept overlapping slices.**
- **Runs of elements in `Modifies`**, such as all the structs a slice of pointers refers to.

### Order of evaluation

Built on 2026-11-19: a call that modifies memory may stand wherever an expression may, in the condition of an `if` or a `for`, the tag and the cases of a `switch`, as an operand or argument, on the right of an assignment to anything, among several results, in the arguments of a `defer`, and on the right of `&&` and `||`. Before, it had to be a statement of its own, the only returned expression, or the whole right-hand side of an assignment to variables.

Decisions:

- **One meaning, or reported.** Go fixes the order of calls, `&&`, and `||` among themselves (lexical, left to right), runs an operation after its operands and the right of `&&` and `||` after the left, and stores the targets of an assignment after every operand. It does not fix when the other reads of memory happen relative to the calls. A read whose value would depend on that order is reported where it is written, as an obligation that failed, not as `cannot verify`. It is never given the meaning one compiler happens to give it; gc reads after the call in every form that was tried.
- **Decided by the value, from the contract.** The operands of one statement, condition, case expression, range expression, or `defer` are one unit. Memory has a version at the start of the unit and after each call that may modify it and each `append` that writes into its array. Each read records from the syntax which versions Go may let it see: from after the latest call or decision of `&&` or `||` among its operands, or the decision whose right side it is on, up to before the innermost call whose receiver or argument it is part of, the decision on whose left it is, or the `append` whose operand it is, and otherwise up to the end. The verifier proves that the read gives the same value in each two consecutive versions of that window, under the guard of the read. It compares values and not places, so a call that writes back what was there does not collide; what a call may change comes from its `Modifies` and `Ensures`. Variables the verifier holds itself are not memory, and no call can change them.
- **The message shows the fix where one fits.** It ends with a statement that makes the read first, as in `, as in n := s.n before it`, with a name that is not visible at the read and not declared in the block that holds the statement. It shows none for a read Go may make on some runs of the statement only, or more than once: on the right of `&&` and `||` (any read under a guard), in a case expression, in the init statement or condition of an `else if`, and in the condition or post statement of a loop. Nor for a read described in words, such as the receiver of a method, or for one that would call something if made again.
- **A read that is not recorded crashes the run.** Every read of memory goes through `table`. While a unit is open, a read there outside `readAt`, or outside `quietly` (what a contract says, and the bookkeeping of a map write), panics with an internal error, whether or not the read tells a state what it learns. So a read site added later without its order cannot pass quietly. The one read Go makes that does not go through `table`, the copy an `append` makes when it moves, is recorded on its own; the other uses of regions outside `table` are writes.
- **A read is as narrow as Go's.** A field of a struct that lies in memory is read alone, and a pointer receiver reached through embedded fields reads only the embedded pointers on the way.
- **An allocation made in a unit** is put into the earlier versions by the same terms. Nothing could refer to it there.
- **Built-in functions are not ordered like calls,** since the specification does not say that they are (decided by the orchestrator). An `append` runs after its operands, and is ordered after the calls of the targets only by a call or a decision of `&&` or `||` among its operands. Its write in place is a version of the unit. When nothing orders it, every call in the targets must modify nothing and have a signature that refers to no memory, with no pointer, slice, or map at any depth of the receiver, the parameters, or the results; otherwise the function cannot be verified. Every read of the targets, including those in the arguments of such a call, is compared with the write. The copy of an `append` that moves is a read like the others. `u[t[0]] = append(t[:0], 5)` verified before and was unsound, since Go may write `t[0]` first; it is now reported. The rule on signatures rests on contracts naming only parameters, results, and error variables: once a contract can name another package-level variable, naming one must count as reading memory.
- **A call on one branch** (the right of `&&` and `||`, a case expression) keeps the single state with guards. Its targets are forgotten as usual, and where the guard fails, memory and the bound of allocations are as they were. No region becomes an `Ite`, so the layers of loops are walked as before. A call of a function literal on one branch joins the state where it did not run with the ends of its body, and a region that differs becomes a constant of its own, which `table` follows like a layer (see Function literals).
- **A variable that a function literal assigns is read like memory.** No other call can change a local variable, but a call of such a literal can. Each version of a unit holds the value of every such variable under a key of its own, and a read of one in an open unit is recorded, as narrow as Go's for a field. A write of the same value does not collide.
- **A condition of a `for` loop that modifies memory.** What it writes is forgotten at the head with what the body writes. The invariants hold where the condition is about to run, and the variant is measured there too, so it must decrease over the condition and the body together: a condition could otherwise undo what the body did. The loop is left in the state after the last evaluation of the condition.
- **The keys of a map literal must differ** unless both are constants, since Go does not fix the order of the entries. `map[int]int{a: 1, b: 2}` with `a == b` verified before and was unsound; it is now reported. A literal whose two keys may be equal is reported even when their values are equal, as in `map[int]int{a: 1, b: 1}`, which has one meaning.

Not built yet: an `append` inside a larger expression (see Structs and pointers); a call in the targets beside an `append` that may write in place, when its contract reads memory, which would need a frame of what contracts read and is not planned; a call with several results as the arguments of another call, `g(f())`; and accepting two keys of a map literal that may be equal when their values are equal.

### Function literals

Built on 2026-11-19: a function literal that is called or deferred where it is written, or that declares a new local variable (`:=` or `var`) which the function only calls. The literal may read and assign the variables of the function and of literals around it, write memory the function may write, and use everything a body may, including loops, `defer`, and further literals of these forms.

Decisions:

- **Verified in place, at each call.** A literal has no contract. Its body is executed at each call, in the state there, as part of the function around it, so every check of the function applies to it, its `Modifies` clauses included, and annotations in it are checked at each call. Each call runs in a frame of its own: `return` ends the literal, its results are assigned to its result variables, its own deferred calls run, and the end state goes back to the call. A diagnostic found in a body names the calls it came through (`, in the function literal called at f.go:L:C`, or `deferred at ... and run at the return at ...`), and the deduplication of reports then lists each failing call.
- **Only where every use is seen.** `literalUses` binds a literal declared with `:=` or `var` whose variable is only called, and refuses a use of such a variable but as the function of a call when the variable has the literal's own type. Every other literal is a value, made where Go converts it to a function type (see Function values). A literal used in place never leaves the function. It can outlive the block it is declared in when it is deferred, but `defer` stays refused in a loop unless it is inside a literal that the iteration calls, so no literal used in place runs after the iteration whose variable it captures. That is why a loop variable is the same for it in Go 1.21 and 1.22. A literal used as a value can run after its iteration; it knows the variable of the iteration only where Go 1.22 gives each iteration its own and nothing assigns it, and otherwise nothing of it.
- **Recursion cannot happen.** A variable is not in scope inside the literal that declares it and cannot be assigned again, so no literal reaches itself. A guard reports one that would. A call of the enclosing function from a literal is recursion of that function, checked against its variant. The analyzer counts a call of an in-place literal as resolved: its body is part of the function's callees already.
- **The ends of a body are joined.** A call inside an expression needs one state. The states the body ends in, and under a guard the state where the call did not run, become one: a constant `path` names the end, the facts each end added hold under `path = i`, and every variable, result, and bound of memory that differs gets a constant equal to that end's value under `path = i`. A region that differs gets a constant recorded with its alternatives in `joins`; `table` states, at each reference it reads, that the region there has the length and every element of the region of the end `path` names, and walks on into the alternatives with a set of what it has seen. So no term holds more than the name of what an earlier join made, and a chain of calls does not grow. The join is a `forward` for `tieFailures`, and a fact stated later at a read of a joined region is added to it. Measured against the same logic written with `if` statements, the join is faster: 2.1 s against 4.1 s on three functions with three ends per call, and 0.37 s against 0.47 s for a deferred literal with six ends run at three returns. Sixteen joined calls on one region take 0.21 s and forty take 0.48 s, where twelve written as `if` statements stop at the limit on paths after 34 s; twenty-five deferred literals with an `if` each take 0.24 s. So the join is used for statement calls too, and a second way that continues once per end was not built (decided by the orchestrator).
- **Captured variables are shared.** They are the function's own, read and written in place. The order rule covers them (see Order of evaluation), a loop forgets what a literal it calls assigns since `effects` walks the bodies of bound literals called in it, and a join merges them.
- **`old(x)` names the parameter at that point.** Inside a body it used to be resolved by name among the parameters, so a variable that hid a parameter, as a parameter of a literal does, was read as the parameter. That was wrong and is now an error.
- **Origins of errors.** A parameter of an in-place literal gets the arguments of its calls as sources, and one of any other literal is unknown. A `return` is a source of the named results of its own frame. A named error result that any literal assigns is judged, at every return, by everything assigned to it, since a deferred literal may change it after the return; any literal counts, which can only make fewer functions publish known errors.
- **`recover` is `cannot verify`** (decided by the orchestrator). In a verified function nothing panics, so `recover` could be given the value nil, but that would need an assumption about the compiler: gc gives nil to a deferred function that runs because its function returned, also while a panic further up is running deferred functions and during `runtime.Goexit`, and the specification's sentence on `recover` read literally allows a non-nil value there. It returns `any`, so the only form gained before dynamic types would be `recover()` as a statement. It waits for the fifth part of interfaces (see the list at the top).

Not built yet:

- A variadic literal, a call of a literal with several results as the arguments of another call, and a literal whose parameters or results have types that are not modelled.
- A call of a literal in the targets of an assignment beside an `append` that may write in place. It is always refused, also when the body changes nothing and reads no memory.
- `recover`, with the fifth part of interfaces.

### Function values

Built on 2026-11-19: a contract on a named function type, in its doc comment; values of every function type held, passed, stored, returned, and compared with nil; calls and deferred calls through a value of a type with a contract; and a function, a method value, or a function literal made into a value of such a type where Go converts it, as in `Apply(xs, double)`, `handlers[name] = h.serve`, `return func(c *Config) { c.Timeout = d }`, and `for _, opt := range opts { opt(&cfg) }`. Contracts of function types travel to other packages as facts.

Repaired on 2026-11-19, with interfaces: a trusted method made into a function value, as in `w.Get`, was not checked like a call written out. `checkHandedOver` asks for `runs` on a receiver that can hold code at a call, but `madeFrom` looked only at the parameters. A trusted `(*lib.Wrapper).Get` that runs a `func()` the wrapper holds, with `modifies: []`, made into a value and called, let a verified caller keep a fact about memory that the function wrote. `madeAs`, where function values and interface methods meet, now requires the receiver under `runs`, and then stratification refuses the method, since it may call through what the receiver holds (773e276; `interfaces/trusted.go`).

Repaired on 2026-11-19, with trust-file contracts for types of other modules: a literal made into a value of another package's function type resolved the error variables of that contract in its own file, so a literal returning `funcvaluesclient.ErrStop` verified against a contract that says `err = nil Or err = ErrStop` of `funcvalueslib`. `madeLiteral` now gives the literal the spelling of its type's contract (`funcInfo.spelled`), which name resolution uses (aaf38ce; `funcvaluesclient/client.go`, `WrongStop`).

Repaired on 2026-11-19, with the next feature: `effects` gave a call through a function value nothing to forget, so a loop, a literal called in a loop, and a deferred value call in such a literal kept what the call's type lists under `Modifies`. `Configure` with `@Ensures cfg.Timeout = 0` verified, and is false. `callSites` now gives such a call the `Modifies` of its type, with roots found as for a static call (18b28f2; `funcvalues/callsdefects.go`).

Decisions:

- **A contract is written on a named type, and only there** (decided by the orchestrator). It travels with the value into parameters, results, fields, slices, and maps, which a contract on a parameter would not. `func Apply(xs []int, f func(int) int)` has to declare a type; a call of `f` says so. The contract names the parameters and results of the signature, its results must be named, and it has `Requires`, `Ensures`, and `Modifies` only.
- **A function value is one reference, zero for nil.** Nothing else is known of it: Go compares function values only with nil, and the behaviour of a call comes from the type. In a formula a value is `FuncVal(ref)`, which `RefEq` unpacks and `Incomparable` refuses beside anything but nil. A struct field of function type, which used to be a hidden leaf, is a modelled leaf; nothing that verified before changed.
- **A call through a value is a call of the type's contract.** It is an event of the unit, its value and arguments are operands before it, the value must not be nil, and its frame is checked against the caller's. Where a verified callee and a trusted one differ, it is treated like a trusted one: the promise is checked against the state, no struct invariant is assumed of what it hands back, its errors have unknown origin, and a weak contract makes it a source of unpredictable failure. An argument that can carry code nobody has seen (an error of unknown origin, a value of an uncontracted function type, an `any`, an interface value with a method that has no contract) is refused, since the value may come from code that is not verified. An interface value whose methods all have contracts is not such an argument (see Interfaces).
- **A value is made in few ways, each checked.** From a function, a method value, or a literal written where Go converts it to the type; from nil; or from a value of an identical type. Anything else is refused, among them `Mapper(p)` for a `p` of another named type with the same underlying type, which would give a value a contract nobody claimed. Making a value of a type without a contract is refused too.
- **A value is checked as a function of its own** (`subVerifier`). Its verifier has its own parameters, entry memory, and allocation bound, at least the one where the value is made. What is known where the value is made comes in as a copy in which every constant and bound variable is renamed with the prefix `^ `, except the constants of error variables and nil. So the copy says what is known of the values the function value keeps, and nothing of the memory it sees when it runs. No name the verifier makes starts with `^`; `fresh` panics on one. A function is checked as a body that calls it, a method value as one that calls it on the receiver evaluated where the value is made, and a literal by running its body. A diagnostic ends in `, in double used as a value of type Mapper at f.go:L:C` or `, in the function literal used as a value of type Mapper at f.go:L:C`.
- **What a literal used as a value captures.** A variable that nothing in the declared function around it assigns but its declaration, whose address is not taken, and that is not a named result keeps the value it has where the literal is made. A `range` variable of Go 1.22 and later counts as declared by its iteration. Any other captured variable is an unknown value of its type; for one in memory the pointer to it is fixed and what it holds is read from the literal's memory. The literal may not assign a captured variable and may not use one bound to an in-place literal, so no call through a value changes a local variable, and in-place literals and the order rule stay as they were. The post statement of a three-clause loop counts as an assignment, which loses the variable of an iteration in Go 1.22. That is a loss, not an error. The design first sketched captured variables living in memory; that is not needed once nothing a value runs can assign them.
- **What a value runs makes no call through a value** (stratification, decided by the orchestrator). No contract of a function type has a variant, and a value could be handed back to code that calls it. So a function, method, or literal made into a value must not reach a call with no static callee, a range over a function, or a call of a function that may make one. `mayCallValues` is the least set of this package's functions closed under calls, from their bodies, trusted functions included, also by `runs` on a parameter that can hold a function; other packages publish `CallsValues` in their contracts. Then a cycle through values needs a value from outside, which is assumed to meet its contract and so to return. The recursion check does not follow value calls, and calls in a literal used as a value are not recursion of the function around it. The same rule settles what a function assumes unchanged across a call that may run a value: a value's writes stay inside its type's frame, and no value can assign a local variable.
- **A contract on a type must be one that can be met.** A value from outside is assumed to meet it, so a contract that no outcome meets for some call its `Requires` allow would make the promise a fact about the arguments, as `2 * y = x` would make `x` even. `canBeMet` proves, from the `Requires` and the types, that some outcome exists: Z3 chooses the results, the new allocation bound, and a new value for each struct or field that `Modifies` lists. Slices and maps keep their contents, so a contract only a change of their elements or memory the call creates could meet is refused. Facts that reading the `Ensures` notes about the entry state are given, not goals. A primed path must read memory that `Modifies` lists, as in a trusted entry.
- **A trusted function and function values.** A result that can hold a value of a type with a contract must be listed under `vouches`, which then claims every such value meets its contract; a `modifies` that covers memory that can hold one, at any depth, needs the parameter of that memory under `vouches`, which claims the same of every such value the function writes or leaves there, and without it the entry is unusable (decided with trust-file contracts for types of other modules, F2). `runs` claims, for every parameter whatever code it holds, that the function runs that code only before it returns, only on the goroutine that called it, keeps no value that can hold code, and calls a function value only with arguments that meet its type's `Requires`. For a function value of a type with a contract, and an interface value whose methods all have contracts, the rest of the claim needs to hold only for values that meet the contracts; for any other code it holds whatever code arrives.
- **Package initialisation.** A value call reached from an initialiser costs the package its sentinels through `hiddenInitCode`, which already reports any call with no static callee, a deferred one included, and any value of the package handed to another package.

Not built yet, each a feature of its own:

- **A literal used as a value whose contract has to speak of what it captures.** Such a literal cannot read captured memory under a fact about it (`s[i]` in bounds for a captured `s`), write through a captured pointer, or count into a captured variable. The contract of a type cannot name what one value captures. A literal handed to a trusted function that calls it while it runs does all of this (see Callbacks handed to trusted functions), since it runs only during the call. For a value that travels, the way in is a contract at the place the literal goes, or a region that stands for what a value captures, which its type's `Modifies` can name and every call that may run the value forgets.
- **A value that calls a value**: decorators, middleware, a literal that hands a value on. It needs a termination argument across values, such as a variant on a function type that each call through a value must decrease, or a depth that values of a type are made at.
- **A trusted function that keeps a value that can hold code**: a registry, a table of handlers, a timer, `context.WithCancel`, and `io.NopCloser`, which keeps its reader in the `io.ReadCloser` it returns (not shipped with state of interface values for that reason). `runs` claims that the function calls what it is given only before it returns, on the goroutine that called it, and keeps it nowhere, so such a function has no true entry, and verified code cannot hand it a value. The reason: a trusted `Register(h Handler)` that keeps `h`, and a trusted `Fire()` with no parameters and `modifies: []` that calls it later, let a verified `V` register a literal that calls `V` and then call `Fire`, which never ends; the claim that would be false sits on `Fire`, which received nothing and shows nothing in the trust report, and `Fire` calls `h` with arguments nobody proves meet `Handler`'s `Requires`. `context.WithCancel(parent)` is the second example, and the one most code needs, for `ctx, cancel := context.WithCancel(ctx); defer cancel()`: it keeps `parent` in the context it returns, the child's `Value` and `Deadline` and `cancel` (through `removeChild`) call `parent`'s methods later, it may register a callback with `parent`'s `AfterFunc`, and for a parent of a type outside the standard library it starts a goroutine that waits on `parent.Done()`. So `runs: [parent]` would be false. Verified code cannot make a `Context` today (Done has no contract), so no code of the caller can be run that way, but the claim is still the wrong one. The way in is an entry that says which value it keeps and which other entries may run it, so that those entries carry the claim, the stratification counts them as making a call through a value, and the report shows both; for `WithCancel` the entries that run it are values, the returned context and cancel function, whose own entries then carry the claim.
- **A contract for an unnamed function type at the place it is used**, such as on a parameter `f func(int) int`, so that existing signatures need no named type. It was left out because a contract on a named type travels with the value into fields, slices, and maps, and one on a parameter would not: a value stored in a field of type `func(int) int` would lose it. The way in decides where such a contract may be written (on a parameter or result of a verified function, perhaps on a field), checks a value against it where it is passed or assigned there as for a named type, and refuses to store or pass on a value of that place into one of another contract, or into an unnamed type, unless the contracts are proved to match.
- **A function type that may be given code nobody has seen.** A call through a value refuses an argument that can carry such code (an error of unknown origin, a value of an uncontracted function type, an `any`, an interface value with a method that has no contract), since the value may come from code that is not verified, which could run that code: `Notify(r Report, e error)` calling `r(e)` with an `e` from a parameter is refused, though an `r` that only logs `e.Error()` looks honest. A declaration on the type, like `runs` for a trusted function, would make the claim that every value of the type holds its contract whatever code the argument carries, with the claim in the guide and in "What a proof assumes"; a value made by verified code meets it already, since its parameters are of unknown origin.
- Also left out: converting a value between two function types, method expressions (`T.M`), generic and variadic functions as values, a variadic function type with a contract, `range` over a function, and a type contract whose `Ensures` only a change of slice or map elements or new memory can meet.

### Callbacks handed to trusted functions

Built on 2026-11-19: a trust entry can give a function parameter a contract under `calls`, as in `f(i)` with `requires: ["0 <= i < n"]`, and verified code can hand such a parameter a function literal written at the call, a function, a method value, or a value of a function type with a contract. The literal is verified where it is handed over, with what is known there, captured memory included. The `ensures` of an entry can speak of what the function returns, as `f(x)`, and an entry can demand a deterministic function with `deterministic: true`. Shipped: `sort.Search` and `sort.Find` (with the binary-search result under the documented premise), and `IndexFunc`, `LastIndexFunc`, `ContainsFunc`, `FieldsFunc`, `TrimFunc`, `TrimLeftFunc`, `TrimRightFunc`, and `Map` of `strings` and `bytes`.

Decisions:

- **A contract under `calls` adds to `runs`, and needs it** (decided by the orchestrator). The parameter must be listed under `runs` too. The claim: the function calls the parameter only with arguments that meet the `requires` under `calls`, in the state at that call, and its contract holds for every function that meets them, returns, and writes nothing its `modifies` covers, whatever else it writes, memory the trusted function reads included. A `calls` key names the parameter and the parameters of its function type, `f(i)` or `do()`. `old` has no meaning in any `requires` of a trusted contract and is refused there, in `calls` and outside. The report prints each contract under `calls` with its clauses apart. A parameter whose type has a contract of its own, a variadic or generic one, one named `is`, `has`, `old`, `fresh`, `within`, or `len`, and a function type that takes or returns something that can hold code are refused.
- **A literal handed over is a third kind** of literal, neither in place nor a value. It runs only during the call, as part of the caller, any number of times, interleaved with the trusted function's writes. So it is held to everything the caller is held to, its `Modifies`, the built-in checks, and recursion of the caller through its variant, and it may read and assign captured variables, as an in-place literal may. A variable bound to a literal cannot be handed over: `literalUses` cannot see contracts.
- **A run is verified once, in a state for every run**, the shape of a loop body without an invariant. The head is the state at the call, before the post-call havoc, with W (what the trusted function's `modifies` covers) havocked again, and `forget` of the union of what every handed function may write (several callbacks may run after each other). The parameters are values of their types that meet the `requires` under `calls`, read in the head's memory. A literal is run by `inline`, the others by `invoke` of their contract in the caller's verifier, so `checkRecursion` sees the caller. The state after the call is a second `forget` of the same set. On one branch of `&&` or `||` the call is made in a clone and joined, as an in-place literal is. The call is an event of the unit that may change memory and captured variables, and it is never pure.
- **A run writes nothing that the trusted function may write** (decided by the orchestrator). Checked by `checkNotForbidden` for every write, also of memory created since entry and of a variable that lives in memory, and for every write of a call inside a run. Without it a contract with `modifies` would not say what the memory holds afterwards. It is also what makes a run that calls `o.Do` on the same `Once` refused, which would never return.
- **Stratification is judged at each hand-over.** A parameter under `calls` does not make the trusted function call through values, and a call in a trusted body through such a parameter is not followed in the call graph. A handed literal is walked as part of the caller, a handed function or method is a call edge, and a handed value is a call through a value. `stratified` judges the same in code that a value runs. A trusted function with `calls` cannot be made into a value: what it would be handed would come from unseen code.
- **Applications are summarised, under a proof of determinism.** `f(x)` is allowed only in an entry's `ensures`, for a function of one integer parameter and one integer or boolean result whose `requires` under `calls` read no memory. At each hand-over, with H the facts a run added, r its result, M the names made for the head and the run, and P the facts about the argument (its type and the `requires` under `calls`), vego proves `H(p, M) ∧ H(p, M′) → r(p, M) = r(p, M′)`, and then assumes `Forall k : P(k) -> Exists M : H(k, M) And F[k] = r(k, M)` with `f(x)` read as `F[x]`. The existence is true in every state that meets the facts at the call. That state is an instance of the head. The body was verified for every instance, so a run from it with any k such that P(k) holds exists, ends, and does not panic, and it satisfies H. Determinism over every M makes `F[k]` what each real call returns, also between writes. A call of the caller inside a run assumes the caller's contract, which is sound by the induction on the caller's variant that every recursive proof rests on. Both proofs use one slice of facts, and determinism compares every leaf of every result. `checkRunNames` panics on a constant in H that is not the argument, not in M, and not older than the call. A check after the runs panics on a fact about any run that reached the caller's state, and another panics when the summaries make a state contradictory that was not, which the argument rules out: a wrong summary would prove anything, so it must not pass quietly. A `deterministic: true` without an application makes the same proof, for an entry whose documentation assumes it (`FieldsFunc`, which crashed before Go 1.10 without it).
- **The head says nothing of memory not yet allocated.** That is why it also stands for a state in which the trusted function has created and written objects of its own. A change that states facts about memory at references from the bound on breaks the summary.
- **What ships says only what the documentation promises for every callback the entry allows.** `Search` and `Find` give their result only under the documented premise (false then true, or positive, zero, negative), and require `n >= 0`, since for a negative `n` the documentation says they return `n` and they return 0 (decided by the orchestrator). The `bytes` Trim functions claim only a length, since a callback may write `s`. The tests check every recorded call against the `requires` under `calls`, answer applications from the harness's own function, and use callbacks that answer at random, and that write `s` for `bytes`.

Not built yet:

- **A way to state what the runs preserve**, an invariant for a callback. Without it, what a callback writes is unknown after the call: after `once.Do(func() { o.val = compute() })` nothing is known of `o.val`, and a counter a callback increments cannot be bounded.
- **Locking a mutex in a run.** A run is verified in a state where what any run writes is forgotten, so a run that locks and unlocks `a.mu` does not know `~held(a.mu)` at its start, and its `Lock` is refused (`locks/locking.go`, `InRun`). It waits for a way to state what the runs preserve.
- **A `requires` of the entry on the callback's result**, demanded of every handed function, such as that `sort.Slice`'s `less` is an order. `sort.Slice` needs the fifth part of interfaces as well.
- **Calling `Do` on a `sync.Once` in a run**, also on another `Once` than the one whose `Do` runs it: the same limit as locking in a run.
- Handing over a variable bound to a literal; applications of other shapes (several parameters, a string argument); callbacks that are given or return an error, an interface, or a function; deferring a call that hands over a function.

### Interfaces

Built on 2026-11-19, the first part of five (decided by the orchestrator; the second part is below, and the rest is items 1 to 3 of the list at the top): interface types other than `error` whose methods write nothing behind their receiver. A contract on a method, in its doc comment in the declaration of a defined interface type. Values of every interface type held, passed, stored, returned, compared with nil, and converted to `any` or along the declarations they have. Calls and deferred calls of a method with a contract through an interface value. And a concrete value converted to an interface whose methods all have contracts, wherever Go converts it, with each method checked there. Contracts of interface methods travel to other packages as facts on the method objects.

Decisions:

- **What a call through an interface value forgets is what its method's `Modifies` lists, and memory created during the call.** The receiver has no name in an interface declaration, so the contract can list only memory that the parameters refer to, and a method that writes anything behind its receiver cannot meet it. That covers every implementation that can be behind the value. One that verified code converted was checked at the conversion, in memory it knew nothing about, so the check holds for any memory at the later call. Any other comes from code that is not verified and is assumed to meet the contract, frame included. The claim is in "What a proof assumes", in words that cover an implementation holding a pointer to a struct that verified code also holds (decided by the orchestrator).
- **An interface value is one reference, zero exactly for the nil interface.** A conversion of a concrete value gives a fresh reference that is not zero, also for a nil pointer, as in Go, and a fresh one rather than a fixed one, so that dynamic types can attach a tag to it later. A conversion of an interface value keeps its reference, so nil stays nil. An error converted to `any` is a fresh reference that is zero exactly when the error is nil. In a formula a value is `IfaceVal(ref)`, which `RefEq` unpacks and `Incomparable` refuses beside anything but nil, so the translation to SMT-LIB has no new rule. A struct field of interface type, which used to be a hidden leaf, is a modelled leaf. A struct with such a field that verified before still verifies (`interfaces/values.go`).
- **`error` keeps its model** (decided by the orchestrator). Its identity, trees, sentinels, and origins are richer than a reference, and moving it would rewrite all of that for nothing. The two meet at dynamic types. An interface whose method set holds the universe's `Error` method is not modelled until then.
- **A contract is read only on a method of a defined interface type at package level without type parameters.** Two interface types written in place with methods of the same names and signatures are identical, and Go converts nothing between identical types. So a contract on one would let a value checked against it reach the other unchecked. For the same reason an interface type written in place that embeds a declared interface is not modelled: `interface{ A }` and `interface{ B }` are identical when `A.M` and `B.M` have the same signature. A value of such a type cannot be made, taken out of a container, or called, so containers of them pass through as before. Refusing them nested in other types would have lost structs with such a field, which verified before. A defined type made from another, as in `type B A`, has `A`'s method objects and their contracts.
- **A contract that an interface leaves out is reported.** When an interface gets a method of one name from two declarations, Go keeps one, and the contract of the other would be skipped without a word.
- **A conversion checks every method of the interface as a method value.** The check is `madeAs`, which function values share. It runs the method of the concrete type on the receiver as converted, in a sub-verifier with memory of its own and a renamed copy of what is known at the conversion, against the contract of the interface method, with stratification. A value receiver gets the converted struct. A pointer receiver gets the pointer, and what it points to is unknown. A value-receiver method held through a pointer reads the struct at each call, after a check that the pointer is not nil, since Go dereferences there. Messages end in `, in (*T).M used as a method of I at f.go:L:C`.
- **What a conversion costs.** Because memory is unknown in the check, these cannot be converted until footprints are built (item 1 of the list at the top): an implementation that writes behind its receiver (`*bytes.Buffer`, a counter, a cache, `byAge.Swap`); a pointer receiver whose type has an `@Invariant`; and an implementation whose `Requires` reads receiver memory. Each is reported as the obligation that fails, not as `cannot verify`.
- **An interface value converts to another interface only along the same declarations, or to `any`** (decided by the orchestrator). Every method of the target must be the very method object that the source has, as through embedding, so the contracts are the same. A target that declares a method itself is refused, and the message names both declarations.
- **`any` can hold anything** (decided by the orchestrator). Nothing can be done with it but hold it, pass it, and compare it with nil, and it counts as carrying code wherever it is handed on.
- **Comparing interface values, type assertions, and type switches are `cannot verify`.** `==` compares dynamic types and values and panics on an uncomparable dynamic type. A switch whose tag or case is an interface and the other is not is refused before either is evaluated, since Go converts the other one.
- **A call through an interface value is a call through a value.** It is an event of the unit with the interface value and the arguments as operands, the value must not be nil (also at a `defer`, where Go panics), it is treated like a trusted call where those differ, and loops forget what its method modifies (`callSites`). `mayCallValues` is true for every interface method, and stratification refuses code that a value made by verified code runs and that calls through an interface value. A struct that embeds an interface value gets methods that call through it, and so does a function type with methods that call the function: both are refused when converted. Decorators wait for a termination argument (item 3).
- **Arguments that carry code.** An interface value whose methods all have contracts can be handed to a function value or to a method of an interface value, as a function value of a type with a contract can. Its implementations are stratified, or assumed to meet their contracts. An `any`, an interface with a method that has no contract, and one whose contract cannot be used are refused, and the message says which.
- **Trusted functions.** A trusted function is given an interface value only under `runs`, as before. A result that can hold an interface value with a contracted method needs `vouches`, and so does a parameter whose memory a `modifies` covers that can hold one (changed with the second part; before, such a `modifies` made the entry unusable). A parameter under `runs` counts as a call through a value only when it can hold a function value or an interface value whose methods all have contracts (narrowed with the second part from "a contracted method"), none of which, since state of interface values, speaks of a state (`makeable`; see State that a value owns, second part): verified code can make a value only of such an interface, so only there can a cycle back into verified code arise. For any other interface, an `any`, or an error, `runs` claims the contract holds whatever code arrives, contracted methods included, so a cycle would make the entry false, which is on its author. That covers a value that verified code converted to a fully contracted interface and that code which is not verified type-asserts to a partly contracted one and hands back, the same shape as for `any`. Uncontracted interfaces, `any`, and errors must be counted once dynamic types let verified code reach what they hold.
- **Every conversion is checked, or the run stops.** Go converts to an interface without saying so in assignments, `var` declarations, arguments, returns, composite literals, map keys, `append`, `panic`, `delete`, sends, `==`, and switches. The type checker keeps no record of it.
  - **The list.** `syntacticConversions` walks those contexts and lists each converted expression with its target type. `eval` panics with an internal error on a listed expression that `evalConverted` is not evaluating, and `evalConverted` panics if the walk did not list that target there.
  - **How go/ssa is used.** go/ssa confirms and does not add. In debug mode every conversion is a `MakeInterface` and every expression a `DebugRef`. One value can carry several expressions, as `x` in `p, t = x, x`, and nothing says which one is converted, so a rule that picked one crashed on valid Go and was dropped. Instead, each non-constant `MakeInterface` must have, among the expressions of its operand before it in its block, one that the walk lists. A function where one does not, or where a value without an expression of its own is converted (one result of several), ends `cannot verify`.
  - **The tests.** `TestConversionLists` checks both directions on the corpus. With `VEGO_STD_PACKAGES` set, it checks the walk's coverage on packages of the standard library; on 28 of them nothing was missed.
- **A conversion at package level is not a hand-over.** `var _ I = T{}` keeps the package's sentinels. Handing a converted value to another package, or calling through one, during initialisation costs them, as before.

Not built yet, besides items 1 to 3 of the list at the top:

- **Footprints of interface values**, item 1 of the list at the top. States of interface values are built (see State that a value owns, second part): every state lies in one region at the row of the value's home, one function of its reference. The plan for footprints, decided with that design: the memory a value owns, with `Modifies w` meaning the footprint of `w`, which then includes the row of its home. For a value made by verified code from a `p` of type `*T`, the row at its home would be tied to `T`'s memory at `p`, by a fact stated at each read as layers do, which is what lets such a value be converted to an interface whose contracts speak of a state; an implementation may not make its footprint grow into memory that existed before the call; a caller that did not make the value treats its footprint as memory assumed separate from its other parameters on entry and proved separate at verified calls; and since a footprint can lie in any region, also one not yet in the `memory` map, memory then needs something like an epoch.
- Calls of methods promoted from an embedded interface field (`w.Price` on `struct{ Pricer }`; call it on the field), methods promoted through an embedded struct field used as methods of an interface, method values and method expressions of interface methods, variadic and generic interface methods, and contracts on generic interfaces.

### Interfaces and function types of other modules (interfaces, second part)

Built on 2026-11-19: an entry of the trust file gives a contract to a method of an interface type, keyed as Go prints the method (`(io.Writer).Write`), or to a function type (`context.CancelFunc`), of another module. Calls, deferred calls, conversions of verified values, loops, order of evaluation, nil, and stratification are those of contracts in source; the contract is a `funcInfo` with `trust` set besides `methodOf` or `valueOf` (`typeentries.go`). Shipped: `(io.Writer).Write`, `(io.Reader).Read`, `(context.Context).Err`, `context.CancelFunc`, and since state of interface values `(io.Closer).Close` (see State that a value owns, second part).

Decisions:

- **What an entry claims** (decided by the orchestrator, then narrowed on review). Every value of the type that verified code gets from code that is not verified, from a caller directly or in memory an argument reaches, or from a call through a value, meets the entry: it returns without panicking, leaves the `ensures` true, writes nothing verified code can see outside `modifies`, and its errors in a result under `vouches` meet the vouches conditions. The frame part is what callers that are not verified can break, by passing a writer together with a pointer to what it writes (a `*bytes.Buffer` as both); that is in "What a proof assumes". The trust report prints the reach in a line of its own.
- **What a trusted function returns or writes is claimed by its own entry** (decided on review, F1 and F2, overruling the first design). A result that can hold a value of a type with a contract, in source or in the trust file, needs `vouches`, and a parameter whose memory `modifies` covers and which can hold one needs `vouches` too, which claims every such value the function writes or leaves there meets its contract. A type entry alone would have put the claim about a project's `NewLineWriter` on the shipped `io.Writer` entry, which nobody reading the function's entry would see. The same rule now holds for contracts in source, which lifted "a `modifies` over such memory makes the entry unusable".
- **Keys and what is refused.** The key must be the declaring interface's: an entry by an embedding interface, an alias, or a type defined from it is reported with the key to use, since only `method.FullName()` is looked up. Generic types, aliases, and types not at package level are refused, as in source. `runs` and `calls` are defects in a type entry (no call through a value is handed unseen code), and `vouches` may list only error results. An entry for a type that has a contract in source is a defect at each use.
- **Only types of other modules** (F4, F6). An entry for a type of the module of the analysed package is reported at the entry and is a defect at use: the project can annotate the declaration. Membership is by the nearest `go.mod` and, where `pass.Module` is known, by the import path lying under the module path, so a vendored package, which `go mod vendor` leaves without a `go.mod`, is another module (`TestInAnalysedModule`). In GOPATH mode the directory decides.
- **Checked like a contract in source, once per package that uses it.** Types modelled, names not ambiguous, `requires` satisfiable, no contradiction, primed paths, and `canBeMet`; faults are defects of the entry, reported at each use in the format of a trusted contract. An entry with defects is not recorded as relied on (F8).
- **One entry per type in a build** (decided by the orchestrator, F3, F10). Without `-vego.trusted` each module reads its own trust file, so a value checked by one module's verified code against its entry could reach another module's verified code that relies on another, which is verified code against verified code and must be checked. Every lookup of a type's entry by a package with annotated functions is recorded in `Usage` with a fingerprint of the entry's text, and so is a lookup that finds none, since a proof made with no entry waived what an entry asks for (vouches on trusted results, the count of stratification). `reportTwoEntries` reports two fingerprints, or an entry against none, in every package built with both; a declaring module with none gets the remedy of a contract in source. Recording at lookup rather than at use sites means a reliance added later cannot be missed. A textual fingerprint errs on the loud side. Packages without annotated functions record nothing, since `io`'s own declarations look up `(io.Closer).Close`. A program whose main package is never given to laas is not checked; the guide says to run laas on it.
- **Stratification counts only interfaces that verified code can make** (decided by the orchestrator, then narrowed on review, F5). Once `io.Writer` has a contract, verified code can make one, so a trusted function with `runs` over something that holds an `io.Writer` may run verified code that calls back. `MakeSink` (`interfaces/trusted.go`), which verified only because nobody could make an `io.Writer`, is refused; this is a narrowing of something that would otherwise be unsound. Its message names the chain of calls and the parameter that is the reason, and says what to do (`valueReasons`, `whyValues`). `context.Context`, with only `Err` contracted, is not counted.
- **Vouches on a type entry.** `knownError` treats the error of a call through a value as of known origin when its contract is an entry that vouches for it. A value that verified code makes of such a type must return only errors of known origin, checked in `madeAs` and, for a literal, by `returnsKnown` under the origins of the enclosing body. Whether a call goes through a value is decided by one predicate, `calledLiteral` then `throughValue`, which `call`, `deferStmt`, `callSites`, and `knownError` share: a call of a variable bound to an in-place literal of a vouching type took the entry's vouch for the literal's error (F9).
- **What a value made by verified code may call.** `errors.New` calls nothing and no longer counts as a function that may call through a value; before, a method or literal made into a value could not make an error. `fmt.Errorf` still counts, since it formats its operands.
- **Shipped entries say only what the documentation says, and are tested against implementations.** `Write`: `0 <= n <= |p|`, `n < |p| -> err != nil`, `modifies: []`. `Read`: `0 <= n <= |p|`, `modifies: [p]`, and `requires: |p| > 0`, because `iotest.DataErrReader` never returns from a `Read` into an empty slice while it holds data, which the documentation (only "should return 0") allows. `Err`: nil, `Canceled`, or `DeadlineExceeded`, what `errors.Is` finds in each, and `vouches`, resting on Go 1.7's "no other values for Err are defined" and on reading the two variables, as `os.Remove`'s vouch rests on source. `CancelFunc`: `modifies: []`. No vouches for `Read` and `Write`: the documentation says nothing of the errors; the guide shows the project entry that vouches and what it claims. Each is tested against several implementations of the standard library and one that does at random all the documentation allows (`shipped_types_test.go`), which fails an entry that claims more than the documentation where the standard library happens to meet it.
- **Not shipped.** `(fmt.Stringer).String`: the documentation states no contract, and `fmt` itself recovers from String methods that panic on nil. `Done`, `Value`, and `Deadline` of `context.Context`: `Done` returns a channel, which is not modelled, and `Value` takes an `any`, which no call through a value may be handed; so verified code cannot make a `Context`, and cannot hand one to a value.
- **`errors.Is` on nil, stated of nil.** For every `is(x, t)` met, `noteIs` also states `is(nil, t) <-> t = nil`, which is true of every target. Without it, `canBeMet` could not choose a nil result for an entry whose `ensures` speak of `is` on the result, since nothing constrained `is(nil, t)`.

Not built yet:

- **`context.WithCancel` and its kind**, which keep their parent (see Function values, a trusted function that keeps a value that can hold code).
- **Channels as values that nothing can be done with**, which `ctx.Done()` and a fully contracted `Context` would need.
- **`is(x, x)` for a comparable target**, the first test of `errors.Is`, and more of an opaque variable (see Errors): `errors.Is(err, context.DeadlineExceeded)` is decided today only by what the `Err` entry states.
- **An entry for a method of a concrete type of another module used as a method of an interface**, beyond what `madeAs` does with a trusted method today.

### State that a value owns

Built on 2026-11-19, the first part (decided by the orchestrator, `(*sync.Once).Do` included as its last step; the second part, states of interface values from code that is not verified with a shipped `(io.Closer).Close`, is built below, footprints and writes behind the receiver are item 1 of the list at the top, and states of the project's own struct types come when something needs them): named states of types of the standard library, declared in the shipped trust files; formulas `held(m)`, `held(a.mu')`, `rheld(rw)`; a rule that verified code never copies or overwrites a value that holds a state; and shipped contracts for `Lock`, `TryLock`, and `Unlock` of `sync.Mutex` and `Lock`, `TryLock`, `Unlock`, `RLock`, `TryRLock`, and `RUnlock` of `sync.RWMutex`, and for `(*sync.Once).Do`. `mu.Lock(); defer mu.Unlock()` and `c.once.Do(func() { c.size = n })` verify.

Decisions:

- **A state is one more leaf of the struct, in a region of its own.** A boolean after the fields, whose cell lies at offset 0 of the struct in the region `typeKey(underlying) + "@" + name` (`partState`, `statesOf`, `state.go`). Everything that handles a struct handles it: zero values and composite literals give False, allocation zeroes it, a havoc of a target that covers the struct forgets it, loops forget it by region, samples of the always-fails check give it a value, and contracts read it through `table`. The translation to SMT-LIB has no new rule. One notion with two layers was chosen over a general one: the state here is a name inside the struct's own memory, and the memory a value owns (the footprint) is a separate, later notion.
- **Declared only in the shipped files, for types with a size and an unexported field.** A state of a struct type in a project trust file is reported: a layout that depends on the module would differ between packages built together. A project file may declare states of interfaces of other modules since the second part, which lie at a home and not in a layout. A type of size zero has no identity, so two of its values could share a state. A declaration is found through the package of the struct's fields, so it must have an unexported field, or a struct of any package could be identical to it without its states; `TestStateDeclarations` checks both.
- **Keyed by the underlying struct, not the name.** `type M sync.Mutex` shares the memory of a mutex and gets the same states, so a write through it cannot leave a state stale.
- **`held` and `rheld` are about the goroutine that runs the function** (decided with the reviewer). `held(m)` is true when that goroutine has locked `m` and not unlocked it since; `rheld(rw)` when it holds a read lock, at most one, since `sync` rules out recursive read locking. Under the condition every proof has, extended so that other goroutines may lock and unlock a mutex this goroutine does not hold and call `Do` on a `Once` this goroutine is not inside `Do` on (what the function handed to that `Do` writes is not excepted), a state changes only through the calls of this goroutine. What a proof of a function that locks shows is stated once, in the guide's section on locks and in "What a proof assumes": the whole proof, the lock discipline included, holds only if no other goroutine writes the memory the function uses while it runs, also while it waits in `Lock`, `RLock`, or `Do`; a contract such as `a.balance' = a.balance + n` after locking is proved and false under contention, and the guide shows it. Every call that waits for another goroutine returns, which a deadlock the verified code takes part in breaks; nobody unlocks a mutex this goroutine holds.
- **No copy and no overwrite of a value that holds a state** (decided by the orchestrator: stricter than vet's copylocks). Copying the leaf with the struct is what Go does with the mutex's fields, and is still not enough. `sync` documents that a mutex must not be copied after first use, so no entry may claim what `Lock` does on a copy; a copy of a mutex that another goroutine holds stays locked for ever while its state, which is about this goroutine, says it is free, so `Lock` on it would be proved to return; and for a `Once`, a run can copy the `Once` while `Do` holds its lock and call `Do` on the copy. An overwrite would change a state other than through a method. `copyWalk` refuses, with a message that says what to write instead, a value of such a type in value context (unless a composite literal, the operand of `&`, an addressable operand of a field selection or a pointer method, or an assignment target), a non-addressable operand of a selection, a call that returns one, a method with a value receiver of such a type and a conversion to an interface that has one, parameters, results, and receivers, `range` and three-clause loop variables, assignments, and `append` to a slice of such elements. go/ssa confirms: every SSA value of such a type is refused unless it is the value of a composite literal, the load from its non-heap `complit` Alloc carrying the literal's DebugRef, and so are parameters, results, and a pointer converted to an interface whose method has such a value receiver. `TestCopiesConfirmed` turns the walk off and requires go/ssa alone to refuse every copy in the corpus. Overwrites, `append`, and a discarded deferred result are judged by the walk alone. Arrays and `copy`, when they are built, must apply the rule: an element copy of `[2]sync.Mutex`, and `copy` of a slice of such structs. Narrowing: code that copied a struct holding a `sync.Mutex` verified before; it was not unsound, since nothing could lock, and no program of the corpus or the guide did it.
- **A formula names an unexported field only in the package that declares it** (F1 of the review). Before, `plan` resolved any unexported field, so `a.mu.mu.state = 0` verified; with other goroutines allowed to lock, that is false, and the fields differ between versions of Go. The package is that of the clause: a body's package, the type's for an invariant, the function's or type's for a contract, also where an imported contract is read, and none for a shipped entry. Nothing in the corpus was lost. A client therefore cannot name `held(v.mu)` for another package's unexported `mu`.
- **States in formulas.** `name(x)` is a state when `x` is a path to a struct or a pointer to one whose type declares it; primed as `has` is, `held(a.mu')`, and `held(old(m))` in a body. A name that is a state of `x` and also a predicate, or a function parameter that a trusted contract applies, is an error; one that is no state of `x` yields to either. The primed-path check of trusted entries counts the state cell where a pointer points, so `modifies: []` with `ensures held(m')` is a defect.
- **Shipped entries require a non-nil receiver and restate every state of the type**, and are tested against `sync` (`locks_test.go`): random sequences of the type's methods, each called only when its requires holds of a ghost the harness keeps from what each call did, with another goroutine contending; each call must return within 5 s, and the ensures must hold. `TryRLock` requires `~rheld(rw)`, since a second read lock would not be counted.
- **`(*sync.Once).Do` has the state `running`, not `done`** (decided on review, F6). `Do` waits for itself when the calling goroutine is already inside `Do` on the same `Once`, which code that is not verified can arrange by calling a verified function from the function it hands `Do`. So a true entry needs a requires about the calling goroutine, `~running(o)`, true while it is inside `Do` on `o`. A state `done`, read as "some goroutine's `Do` has returned", would change while a verified function runs; read per goroutine it would say nothing useful until a way to state what runs preserve exists, so it was left out. The entry claims nothing about whether the function runs beyond what `calls` allows: at most once, before `Do` returns, or not at all. A run cannot call `Do` on the same `Once`, since it may not write what `Do` writes, nor copy it, by the copy rule. The test runs rounds on fresh `Once`s, half of them with another goroutine in `Do` on the same `Once`, and requires each call to return, the function to run at most once, and `Do` to return only after a run finished.
- **The trust report lists the states** that the parameters of the contracts in use declare, with their meaning.

Built on 2026-11-19, the second part: states of interface values from code that is not verified. A state is declared on an interface type with `@State name` in source, in a `state` section of a project trust file for an interface of another module, and in the shipped files, which declare `closed` of `io.Closer`. A method's contract names its receiver with `@Receiver c` or `receiver: c` and speaks of its states as `closed(c)` and `closed(c')`, with `Modifies c`. `(io.Closer).Close` ships with `requires ~closed(c)`, `modifies [c]`, and `ensures closed(c')`. `defer resp.Body.Close()` verifies under shipped entries for a body known not to be closed, from a `Requires` or from a trusted function whose entry says `~closed(resp.Body) And fresh(resp.Body)` (`ifacestate/`, `guide/states.go`).

Decisions:

- **A state lies at the home of the value, in one region for all states** (decided with the reviewer, F2 of the design review). `home(r)` is a read of a constant sequence that nothing writes, at the reference, so equal references have one home and the translation to SMT-LIB has no new rule. Every state of every interface value is a Bool cell in the region `"iface state"`, at the row of the home and at a position that is the number whose base-256 digits are the bytes of the qualified name (`"io".Closer@closed`), the same in every package and injective since no name has a zero byte. One region was chosen over a region per declared state because a call through `io.Closer` must forget a state that a package may never have heard of (a project's `Session` that embeds `io.Closer`), and a region missing from `memory` would read as its entry value. The ROADMAP's sketch had two functions of the reference; one suffices once the position is the state. Every interface value has `0 < home(r) < brk`.
- **`Modifies c` for an interface value is the whole row of its home** (`target.row`, `site.row`), every state whoever declared it. A method whose contract does not list its receiver keeps the row. That is the claim a declaration makes, written in the reason of `closed`, the guide, the trust report, and "What a proof assumes": every method of a value with the state whose contract does not list the receiver leaves it unchanged. For `closed` that says `Read` and `Write` never close the value, which the documentation does not say. The frame check matches rows by reference, and no field target has the region's key. A path that ends in an interface field covers the states of what it holds and not the field, as a pointer field covers its struct, so assigning `h.W` under `Modifies h.W`, which verified before, is refused with a message that says to list `h` (a narrowing, decided by the orchestrator; no program of the corpus did it). A path that ends in a function value still covers the field. A verified function's `Modifies r` for an interface without states is an error; a trusted entry may list any interface value, for a function that type-asserts it and closes it (F5).
- **Which values share a state.** Equal references: a copy, a conversion between interfaces (which keeps the reference), and a value held in an `any`. Two parameters whose types have states, of which the contract lists one as a row, are assumed to have homes of their own unless one is nil, and every call proves it, verified or trusted (`sharing`, `apartHomes`). The nil case matters: two nil values share `home(0)`, and without it the assumption would make "both nil" impossible. The assumption is strict, as for slices: one value passed as both is refused (a narrowing of the design's "equal references or apart homes", under which no function closing two parameters could be verified), and an unverified caller must not pass one value twice, two values that hold one value, or a wrapper and what it wraps. A pair of which the contract lists neither is not assumed apart, since such a contract changes no state of either (F8 of the review): `Pump(rwc, rwc, buf)` verifies. Values in memory and results of calls are not assumed apart from anything; `fresh(x)` for an interface value, `home(x) >= brk` before the call, says that what it holds was created by the call.
- **Values made by verified code are refused when a contract in use speaks of a state** (rule B, decided by the orchestrator with the reviewer's condition). Converting a value of a concrete type to an interface is refused when a contract in use for one of its methods names its receiver; nothing ties a state to the implementation until footprints. `makeable` decides both that and what stratification counts (`holdsCallable`, `callableIn`), so a project whose own `(io.Closer).Close` entry names no receiver can convert its closers, and a trusted function with `runs` over them counts as calling through a value (`closer/`). Under the shipped entry an `io.Closer` is not counted, which kept trusted functions with `runs` over a `*http.Response` verifying.
- **Declarations.** Only on a defined interface type at package level without type parameters that declares a method itself (`declaresMethod`, F1); `type B io.Closer` has io.Closer's methods and cannot. Two states of one name on an interface are reported at it, and a formula that cannot tell them apart is ambiguous. States in source travel as `stateFact` on the type name. A project trust file may declare states of an interface of another module (decided by the orchestrator, O3); not of a struct, of an interface with shipped states, of one with states in source, or of one of the analysed module, each reported at the type's line. Keys are normalised, `example.com/lib.Conn` and `"example.com/lib".Conn` alike.
- **One declaration per interface in a build** (F3). A package with proofs records `states of D` with a fingerprint of D's declarations from the trust files, or that it found none, whenever it asks which states a value has, and at every call through an interface. `reportTwoEntries` reports a difference with wording of its own. Shipped and source declarations are the same in every module.
- **Samples of the always-fails check** give each interface value with states a reference and a home of its own and a value Z3 chooses for each of its states (F7), and `canBeMet` gives each known state of a listed row a value Z3 chooses.
- **Shipped `Close`, tested.** `closer_test.go` runs random sequences of `Read`, `Write`, and `Close` on 13 implementations (files, pipes, `net.Pipe`, gzip, zlib, flate, `io.NopCloser`, an `http` body, and one that does at random all the documentation allows), `Close` only while the ghost says not closed, each call within 5 s; `Read` and `Write` must meet their entries before and after `Close`. A second `Close` is logged, not checked: `*os.File` returns "file already closed", the flate and zlib writers "closed writer", most others nil, and the closer that does everything the documentation allows panics. No implementation broke `Read` or `Write` after `Close`.
- **An `Ensures` conjunct that speaks only of the entry state** is refused when it reads memory the contract may modify (see The annotation language).
- **A tactic out of resources is a limit, not a fault.** Z3 replies `(error "tactic failed: max. resource limit exceeded")` with no status when a tactic of the chain runs out; exactly that reply now counts as unknown, and any other error is still a fault (`TestProtocol`).
- **Cost.** A chain of 30 calls that change states of new values takes about 11 s, from the sat checks after trusted calls through 30 row stores (`semantics/chains.go`); 30 parameters under `Modifies` took 20 s from the existing 30-by-30 checks of whether each entry is needed. A trusted function that returns a `*http.Response` and an error took about two minutes to verify one caller, at a76cc6b already (162 s) and at the end of this feature (125 s). Since F12 it takes 0.16 s, and the check of the entry 0.34 s; see Problems in which a region holds sequences are solved without extensionality, under The prover.

Not built yet:

- **Locking in a function handed to a trusted function**, such as the function that `sort.Search` calls, a mutex that exists when the trusted function is called, or calling `Do` on such a `Once`. A run is verified in a state where what any run writes is forgotten, the mutex included, so `~held` is not known there; a mutex the run creates itself can be locked. It needs a way to state what the runs preserve (see Callbacks handed to trusted functions).
- **States of the project's own struct types and of types of third-party modules**: an annotation on a struct type, travelling as a fact, and a rule for how the type's verified methods set it, either a ghost statement or a definition as a formula over the type's own fields, which needs no ghost code (to be weighed when it is built); for third-party types a declaration in the trust file, with one declaration per type in a build, stricter than entries since the layout depends on it.
- **States other than booleans**, such as a count of read locks.
- **`sync.WaitGroup`, `sync.Cond`, and the rest of `sync`**, which need goroutines.
- **A formula that two interface values share no state**, as `apart(a, b)`, so that a `Requires` can say it of values in memory, and fields and elements assumed or proved apart. Today `rs[0]` and `rs[1]` may share one, and closing one makes the other unknown.
- **`fresh` that keeps two results apart from each other.** Two `fresh` results of one call may share a home.
- **Converting a value of the project to an interface whose contracts speak of a state**, with footprints (item 1 of the list at the top).
- **Shipped entries for other interfaces with a protocol**, among them `net.Conn`, which declares a `Close` of its own and so has no `closed`.
- **A type assertion that keeps the reference**, with dynamic types (item 2), so that `x.(io.Closer)` of an `any` has the states of what it holds.

### Maps

Built: maps with integer or string keys and values of any modelled type; reading, the two-result read, writing, `delete`, `len`, `make`, literals, nil, `range`, `Modifies`, and `m[k]`, `has(m, k)`, and `|m|` in annotations.

Decisions:

- **A map is a reference into memory of its own.** For each map type there is a region saying which keys each map has, one for each leaf of the values, and one for the number of keys. Two maps may be the same map, like two pointers.
- **A string key becomes a number.** The logic has a function that gives every sequence a number, the same for two sequences exactly when they have the same length and elements. That is all the solver knows about it.
- **An absent key has the zero value**, so `m[k]` needs no case distinction. This, that the count is not negative, that a present key makes it positive, and that the nil map is empty are stated for each map and key that is read.
- **The count is only tracked through writes.** A write adds one if the key was absent and a delete takes one off if it was present. Nothing ties the count to the set of keys beyond that, so a fact such as "two distinct present keys mean at least two keys" cannot be proved.
- **`delete` on the nil map does nothing**, as in Go. In the model the removal writes that the key is absent and has the zero value, which is already true of every key of the nil map, so no rule about the nil map is ever broken.
- **`range` over a map is a counted loop over unknown keys.** Each iteration gets some key that is present. That the keys of different iterations differ is not modelled, so a loop cannot prove that it saw every key. A loop that writes a map of the ranged type is rejected, since Go's rules for that are involved.
- **Samples of maps have one key.** The search for an input on which a contract forces success tries the nil map and maps with a single key. In a value that is a struct each number is picked on its own, and everything else in it is zero.

Not built yet: keys of other types (booleans, pointers, structs); a way for an invariant to count the iterations of a `range` over a map, without which a loop cannot add up the values of a map and prove that the sum does not overflow; elements of a map in `Modifies` paths with string keys; and maps of maps beyond what the value model gives for free.

### Struct invariants

Built as decided below, including invariants of types of other packages, which travel as analysis facts with the constants they mention. A declaration is checked once: an invariant that cannot be read, or a set of invariants no value satisfies, is an error even if nothing uses the type.

Decisions:

- **Not assumed after trusted code.** A verified function proves the invariants of what it hands back, so its callers may assume them. A trusted function proves nothing, so after it the invariant of a result, or of a struct it may have modified, has to be proved again before it is relied on.
- **Only at boundaries, only for what is passed directly.** The invariant is applied to parameters, receivers, and results whose type is the struct or a pointer to it. A struct inside another struct, in a slice, or behind a pointer field is not covered.
- **Declared on the type.** `// @Invariant 0 <= Count And Count <= |Items|` in the doc comment of a struct type, naming its fields directly.
- **Shorthand for contract clauses at every boundary.** The invariant is assumed on entry for every parameter and receiver of the type, proved on return for those and for every result of the type, and proved at each call for every argument. Between those points it may be broken. It is only ever assumed where a verified caller has proved it. Like a `Requires`, it is taken on trust from callers that are not verified.
- **Always enforced, for every function, with no opt-out.** An opt-out would let the invariant be switched off function by function while the type still advertises it. A helper that must run while the invariant is broken takes the fields it needs instead of the struct, or the caller restores the invariant before calling it. Revisit only if real code cannot be restructured that way.
- **Best on a struct's own fields.** An invariant may mention what a pointer field points to, but any call that might modify that target makes the verifier forget the invariant. Ownership between structs is deferred with linked structures.
- **Likely to absorb the boilerplate about slices a struct holds.** With the memory model as built, a method that appends to `s.items` has to promise `fresh(s.items) Or within(s.items', s.items)` so that the next call may write the slice again. An invariant that says a struct owns the array of its slice would state that once. That is ownership of memory, the footprint of item 1 of the list at the top, and not a named state: state that a value owns, as built, names a boolean inside the struct and says nothing about what its pointers and slices refer to.
- **An invariant can read a state**, as in `@Invariant ~held(mu)`, which is then assumed and proved at boundaries like any clause.

### Trusted contracts for unproved code

Decision: a trusted contract covers the function's own code only. A value that can hold an error, an interface, or a function brings code that the author of the contract has not seen, so it is passed to a trusted function only when the contract lists the parameter under `runs`, which makes the wider claim explicit and puts it in the trust report; an error of known origin is exempt. An outside audit produced a wrong proof with an honest-looking `modifies: []` entry for a function that called `err.Error()`. A parameter without a name cannot be listed, so such a function needs a wrapper.

Built: the trust file and its checks, the rule that a call needs a contract, contracts for functions and methods, contracts for methods of interfaces and function types of other modules (see Interfaces, second part), the shipped contracts with their tests, the shipped contracts for locking `sync.Mutex` and `sync.RWMutex` (see State that a value owns), the trust report (`laas -vego.trust`), `vouches`, and error variables named in trusted formulas by the path of their package. Not built yet: `http.Get` and the methods of `http.Client` that return a response (decided not to ship with state of interface values, O4): their `vouches` on the result would claim that every function value and interface value a `*http.Response` holds, `Body` with its `Read` and `Close`, `Request.Body`, `Request.GetBody`, and the request's context, meets its contract, which needs the reading of `net/http`'s source that `os.Remove` needed of `syscall`, and an entry `err = nil -> resp != nil And resp.Body != nil And ~closed(resp.Body) And fresh(resp.Body)`; shipped contracts for methods of other concrete types (the test of shipped contracts calls functions, the methods of the mutexes, and values of the interface and function types that have entries); shipped contracts that vouch for the errors of more functions, which need the same reading of source as `os.Remove` did; checking a trusted `modifies` against the function's source, and running the shipped-contract tests on several Go versions. Error variables of other packages, such as `io.EOF`, need no entry: they are read from the source of their package.

Contracts of verified functions cross package boundaries as analysis facts, together with the predicates of their package; the predicates of different packages are kept apart by a prefix.

Formulas in the file have to be quoted, because YAML gives its own meaning to `: `, `|`, `!`, `[`, and `#`.

Verified code has to call code that cannot be verified: the standard library, third-party modules, and functions of the project itself that use unsupported Go. A trusted contract states what such a function requires and ensures. Callers must still prove the `Requires`; the `Ensures` is assumed rather than proved.

Decisions:

- **One file, no in-source trust.** Contracts for unproved code live in `vego-trusted.yaml` next to `go.mod`. There is no in-source `Trusted` marker and no `Assume`, so every assumption is a diff in one conspicuous file. A function with both annotations and an entry is an error.
- **Entry format.** The key is the function's full name as Go prints it (`sort.Ints`, `(*bytes.Buffer).Len`). Fields: `reason` (mandatory free text saying why the contract is believed), `requires`, `ensures`, `modifies` (what the function may write, in the form of a `Modifies` clause; anything unlisted is assumed untouched), `runs` (parameters whose code the function may run), and `vouches` (error results whose errors the author vouches for). Formulas use the annotation language. Parameter names come from the real signature; there is no override.
- **Result names.** Named results keep their names. A trusted function may have unnamed results, since its signature is not ours to change: a single one is `result`; several are `result1`, `result2`, ...
- **No contract, no call.** Verified code that calls a function with neither annotations nor an entry is an error, never silent trust. When in doubt, vego takes the loudest path: agents loop on its output, so anything quiet gets exploited.
- **Checks on the file.** The function exists, every name is a parameter or result of the right type or an error variable that exists, whose package is in the build and that the caller may rely on, `modifies` is present, even if empty, and names memory a caller can see, a primed path in an `ensures` reads memory of a kind that `modifies` lists, every name under `vouches` is a result of type `error` listed once, and no contract contradicts itself.
- **Checks at each call.** After the promises of a trusted contract are assumed, a quick attempt is made to prove a contradiction; if it succeeds on a path that was not contradictory before, the call is reported. The attempt is bounded, so a contradiction that is hard to find gets through.
- **Recursion through a trusted function of the same package is found.** Its body is there to read: a function it names, or that a call it cannot resolve may reach because the package names it somewhere other than to call it, counts as called. A call back by way of another package is not seen and is part of what is trusted.
- **What a trusted function is trusted with besides its contract.** It returns without panicking when its `requires` hold, which includes not calling back into its verified caller by way of another package, writes nothing a caller can see beyond its `modifies`, and keeps no pointer or slice it was given. Nothing is assumed about where a pointer it returns points.
- **`runs` also says when the code runs.** A function that keeps code it was given under `runs` and has another trusted function run it later puts the claim on an entry that received nothing and shows nothing in the report. So `runs` claims, for every parameter whatever code it holds, that the function runs that code only before it returns and only on the goroutine that called it, keeps no value that can hold code, and calls a function value only with arguments that meet the `Requires` of its type. A function that registers a callback cannot honestly list it. The hole is older than function values: at c7c0e2d a trusted `Keep(e error)` with `runs: [e]` could keep an error that a trusted `Flush()` with `modifies: []` then formatted, and the proof of a verified caller of both relied on `Flush` writing nothing. `Keep`'s entry was true as `runs` was worded then, and the false claim sat on `Flush`, which received nothing and shows nothing in the trust report. It was closed by the wording, which makes `Keep`'s entry the false one; `funcvalues/keep.go` holds the program. vego cannot check the claim.
- **Shipped contracts.** Standard-library contracts are YAML files in this repository, one per package, embedded in the binary. A project entry replaces a shipped one. They state documented behaviour only, written from the documentation of the oldest supported Go version; the Go 1 compatibility promise then keeps them true on every later version, so there are no per-version variants. Each is tested against the real function on random inputs, on every supported toolchain once CI exists.
- **Not shipped.** Contracts for third-party modules, which carry no such promise.
- **Trust report.** `laas -vego.trust ./...` prints the project entries, the shipped entries in use, and unused entries.
- **`vouches` claims what verified code needs of an error, and no more.** An entry lists error results whose errors verified code may format, wrap, search with `errors.Is`, compare with any error, and hand to another trusted function. The claim, for every non-nil error returned there, every error in its tree, and every value these hold: every method returns without panicking and writes nothing a caller can see, whatever it is passed (so an `Is` method calls no method of its target); `==` on these errors cannot panic and is identity, so `errors.Is` answers the same for errors, and for targets, that `==` reports equal; and what `errors.Is` reports does not change after the call. A two-tier design, in which a vouched error would not be exempt from `runs`, was considered and dropped: it doubled the origin machinery for one rare use. The claim is stated in the guide in words to check against source, and in "What a proof assumes".
- **Names in a trusted contract are paths.** A trusted contract means the same in every package that calls it, so its names cannot depend on what the declaring package imports, which changes between Go versions and systems (`strconv` imports a package named `strconv`). A bare name is an error variable of the declaring package; `io.EOF` names one by a path that is an identifier; any other path is quoted, `"io/fs".ErrNotExist`, `"example.com".ErrRoot`, which parses as a field of a string literal (`/` is division). A quoted identifier is refused, so each name has one spelling, and so is a quoted path outside a trusted contract. The package must be in the build of the caller.
- **A shipped vouch may rest on reading source.** Documentation rarely says which types the errors of a function have, and what their methods do. `strconv.Atoi`'s claim follows from its documentation (a `*NumError` whose `Err` is one of two sentinels); `os.Remove`'s rests on its documented `*PathError` and on reading what package `syscall` puts in it. `shipped_test.go` walks the tree of every vouched error the harnesses produce and requires each dynamic type to be in a list of types whose methods were read, so a new type in a later Go fails the test until someone reads it.

### Errors

Built: errors with an identity. Code compares them with `==`, `!=`, and `switch`, calls `errors.Is`, and reads the error variables of its own package and of every package it is built with. Contracts say which error is returned, with `err = ErrEmpty` and `is(err, ErrEmpty)`. Also built: non-nil results for `errors.New` and `fmt.Errorf`, the trees of what `%w` wraps, the always-fails check with its exception, every error variable that is never assigned (made, alias, or opaque), and errors of trusted calls that the contract vouches for (see Trusted contracts). An error inside a struct result is not looked at by the always-fails check.

Decisions:

- **Identity is equality.** Two errors are equal in the logic when they are the same error, which is what Go's `==` reports when one side is a pointer. Code may compare two errors only when one of them is `nil`, a sentinel, of known origin (made, or vouched, whose claim says `==` is identity), or an opaque variable whose initialiser has a pointer, integer, string, or boolean type or an array or struct of these. Two errors of which nothing is known may hold the same uncomparable type, and are refused. Floats are excluded since `==` is not identity on them (NaN, and 0 against -0), and so are channels, to keep the stated rule short. A formula may compare any two errors, and there `=` is identity.
- **Every call makes a different error.** An error made in a body differs from every sentinel, from every other error made in the function, and from every opaque variable met, which held its value since initialisation: the facts are stated pairwise as each appears. It is not known to differ from a parameter or the result of a call. Stating that needs an allocation fact on every error read, which was left out until a contract needs it. An opaque variable is not known to differ from a sentinel, since `var ErrF = id(ErrMine)` holds one.
- **A variable that is never assigned holds one error.** findSentinels classifies every package-level variable of type `error` that its package never assigns or addresses: made (an initialiser of `errors.New` or `fmt.Errorf`, the sentinel as before), alias, or opaque, and publishes all of them in `sentinelsFact`, with what changes the others (`Changed`), so the write and reliance machinery covers every kind. An alias is a variable whose initialiser names another error variable, or calls a parameterless, non-generic function of the same package whose whole body is `return V` (`fs.ErrNotExist = errNotExist()`); it is that variable's constant, so `os.ErrNotExist`, `fs.ErrNotExist`, and `oserror.ErrNotExist` are one sentinel. The form was kept that narrow on purpose: no longer bodies, no chains of calls, no functions of other packages. An alias whose target cannot be relied on is opaque: it copied one value at its initialisation, and its proofs do not rely on the target. An opaque variable is a constant with nothing assumed but what the static type of its initialiser gives: not nil when that type is concrete (a nil pointer included), and comparable as above. Its methods are unknown, so it is not formatted, not the first argument of `errors.Is`, and not handed to a trusted function. Settledness covers every kind; in `hiddenInitCode` only made sentinels and aliases of them, or of variables of other packages, count as holding no code of the package, and anything else goes through its initialiser.
- **Known origin has two kinds, and every conclusion needs only what both give.** Made: errors.New or fmt.Errorf made it from plain values and made errors, so its methods and those of its tree are the standard library's. Vouched: a trusted contract vouches for it, it holds such an error in its tree, or a verified function returned it. Formatting, the first argument of `errors.Is`, the safe side of `==`, handing to a trusted function without `runs`, and `KnownErrors` rest only on methods and `==`, which both kinds give. What needs a made error (not nil, differs from other errors, what `errors.Is` finds) is never drawn from known origin; it is noted where errors.New and fmt.Errorf are called and for sentinels.
- **Sentinels come from source, for every package.** `laas` analyses every package a package is built with, the standard library included, so `findSentinels` runs on `io` as on the package itself. Each package publishes its sentinels, what each one's error rests on, and its tree in a fact about the package. A fact about a variable reaches only the direct importers of its package, which left `io.EOF` unknown in a package that imports `io` only through another. Trust entries for variables were considered and not built: a fact read from source is stronger than a claim and covers third-party modules too. Settledness is a matter of the declaring package only. Go initialises a package before any code of its importers runs, so an importer reads a sentinel that is unsettled in its own package as a sentinel.
- **A write anywhere in the build is seen.** Every package publishes its writes to the error variables of other packages, assignment and `&` both, and the proofs that rely on sentinels publish which keys they rely on, with every sentinel that went into them. A package refuses a sentinel that it, or a package it is built with, writes, also through what went into it. And every package reports each write in its build that some proof in its build relies on, so running `laas` on a root package alone reports a write in one dependency to a sentinel that another dependency relies on. What remains assumed is code outside the build and writes through `go:linkname`, assembly, `unsafe`, or `reflect`.
- **`errors.Is` needs a known origin in its first argument.** It runs the `Is` and `Unwrap` methods of the tree it searches, and calls nothing on the target, so the target may be any error. Its result is `is(x, t)`.
- **Trees by ground instances.** For each error whose tree is known, which are the errors made in the body and the homemade sentinels, and each target met outside a quantifier, the verifier assumes `is(e, t) <-> (e = t Or (w != nil And is(w, t)))`, or `is(e, t) <-> e = t` when nothing is wrapped. For every `is` term it also assumes that `is(nil, t)` is `t = nil` and `is(x, nil)` is `x = nil`, which is `errors.Is`'s first test and calls no method. A quantified axiom was not used: Z3 then answers `unknown` where the search for inputs needs `sat`. A target bound by a quantifier gets no instance, which can only keep something from being proved. The facts stay in the facts of the path, so the dependence check's renamed copies keep them.
- **The format is read, or the tree is not known.** `formatWraps` follows fmt's `doPrintf` for the formats it can read without doubt: flags, a width and a precision of at most six digits each (fmt stops reading a format at a number past a million), a verb that is any rune, `%` taking no operand, at most one `%w`. Anything else, such as a format that is not a constant, `[n]`, `*`, or several `%w`, gives an error of known origin whose tree is not known, so `errors.Is` on it is an unknown boolean. Nothing that verified before this became `cannot verify`. A call without an error operand wraps nothing whatever its format. The rules hold from Go 1.13 on. `TestFormatWraps` checks them against the running `fmt.Errorf` and `errors.Is` on random formats drawn from the forms fmt reads in more than one way, and `TestErrorsAsModelled` checks what the model takes from the implementation and not from documentation: every result is a new pointer, none has an `Is` method, and `Unwrap` returns what the tree says.
- **Inputs of the always-fails check.** Each error of a sample is `nil`, a sample error of its own, the error of an earlier leaf, or an error variable the formulas mention and tie to an error of the input: two constants that hold errors are tied when one formula mentions both, transitively. Offering every variable the formulas mention made the shapes pass `maxShapes` once `strconv.Atoi`'s contract named `ErrSyntax` and `ErrRange`, and a function with two error parameters lost its excuse; a variable tied only to what calls returned cannot be needed by a fact about the input. The sample errors are known to be non-nil and pairwise different, which separate `errors.New` values are. Error variables count as inputs, and the facts about them alone are part of what is known of every input.
- **Contracts name sentinels by their spelling where they were written.** A contract of this package resolves `ErrEmpty` and `io.EOF` in the file of the function. An imported contract carries the key of each spelling (`contractFact.Errors`), so an importer's own `ErrGone` cannot capture it. A struct invariant may not name an error variable yet, and a predicate names only its parameters.
- **Only an error of known origin can be formatted.** `fmt.Errorf` runs the `Error` method of an error it formats and, with verbs such as `%#v`, methods of the values the error contains. An error passed in from outside could use them to write memory the function reasons about. An error may therefore be formatted only if it was made by `errors.New` or `fmt.Errorf`, here or in a verified function that returns nothing else, is a package-level variable of any package holding such an error, or is one that a trusted contract vouches for. That is decided from the text of each function, without regard to the path taken: a variable qualifies when every assignment to it does. Errors from parameters and from trusted functions that do not vouch for them can be returned and compared with `nil` or a sentinel, but not formatted or searched with `errors.Is`. The same rule decides the first argument of `errors.Is`.
- **A contract must not allow a function to always fail.** For every verified function that returns an error, vego checks whether an implementation that always returns a non-nil error and zero values would satisfy the postcondition. If it provably would, that is an error, not an opt-in audit finding. The fix is to state when the function succeeds, as in `err = nil <-> 0 <= i < |A|`.
- **Exception: success that hangs on the outside.** A function cannot promise success when a call nothing predicts decides it: a trusted function whose contract leaves open what comes back, or a verified function that is itself excused. The call must decide between failure and success: some return of an error and some return without one must each depend on what the call produced, and each must be reachable by some input. Reaching the call is not enough, and a function that fails whatever the call does is not excused.
- **Reaching the call is judged generously.** Only the conditions on the function's own inputs must be satisfiable by a concrete input. When the path to the call depends on values the verifier does not know, such as the result of an earlier call, the path counts as possible. A call that is in fact dead behind such an unknown can therefore excuse a weak contract. So can a call that in fact always succeeds when seeing that takes facts about memory more than one pointer away from its arguments: what the types guarantee is supplied for the arguments, for the elements of their slices, and for the objects their pointers refer to, but not further. Both make the check miss a weak contract; neither makes a proof wrong.
- **Depending on a call is decided by proof.** Whether a returned error is nil, or the condition of a branch that was a real choice, depends on a call when it cannot be proved to stay as it is once everything the call produced is replaced by other values the call could have produced. What a call produced spreads to what a later call returns that was handed any of it, and to the unknowns that loops put in place of variables. It is not followed through memory that a later call reads or that a loop writes; a function that depends on the call only in that way is reported and has to be restructured.
- **The check asks only what is read** (decided with speed, by the orchestrator). What `noteFailureSource` and `tieFailures` find (the calls whose failure nothing predicts, and whether the function fails because of one) is read only by the report of a contract that may always fail, and only for a function that returns an error. So they ask nothing unless such a function is being verified (`tracksFailure`); in a function that returns no error, in an audit, in the check of a value made from code, and in every other task they return at once. One thing is still done there: whether a trusted contract, or the contract of a type, forces success for some input is settled for each callee with an error result (`trustForces`), since the trust report reads it for its note `[may fail unpredictably]`. Skipping questions changes the comments of later problem texts, which carry numbers the process hands out, and never their answers: Z3 reads no comment. Together with the next bullet, it brought the main corpus run from 22,309 problems asked and 369 M units counted at 35dca07 to 20,263 and 226 M at the end of speed (the same packages; `manywrites` came later).
- **Whether no state forces success is asked only for a contract that is reported.** When the search finds no input, `forcesSuccess` leaves that further question, the costliest of the check (a quantified question that ran to the limit 31 times on the corpus at 35dca07), as a function that `reportAlwaysFailing` calls for a contract it reports, with the facts and options built when the function was verified, and counts against the function. Its answer only chooses between "it requires success for no input" and "no simple input was found". `trustForces` never asks it, since it reads only whether an input was found. Of the 201 times the corpus asked it at 35dca07, 53 were for contracts that are reported.
- **The questions come in the same order on every run.** A loop records what an iteration leaves in each variable it forgets in the order of the variables' names; it took them in the order of a Go map, so `tieFailures` asked the same questions in another order on another run, and once 56 questions against 58. The answers never differed. The guard of the corpus costs (see The prover) fails when an order changes what a function asks, as this one did; an order that asks the same questions in another sequence changes no count and no answer.
- **A sentinel is trusted only when nothing can run before it is set.** `var ErrX = errors.New("x")` is non-nil for a verified function unless code of the package can run during the initialisation of its variables in a way Go's ordering does not see. Code of a package reaches another package only by being handed over, so every hand-over in code that runs during initialisation costs the package its sentinels: an argument, receiver, or type argument of another package's function, an assignment to another package's variable or to anything but a plain variable, a send, a built-in that passes its argument on, and a call or range that cannot be resolved. A value whose type has no room for code is not a hand-over.

- **The outside world is unknown, not modelled.** A call whose outcome depends on something that is not an argument (a file, the network, the clock) returns some value satisfying its contract, fresh on every call. Proofs must hold for every such value. vego does not model the state of the world.

Not built yet:

- **More of an opaque variable.** Its methods could be read from source like a sentinel's, so that `context.DeadlineExceeded`, whose type has only `Error`, `Timeout`, and `Temporary`, could be formatted and searched. That needs a reading of every method of the type and of what it holds, which is the vouches claim made by the verifier instead of an author. Not planned until a use appears.
- **`errors.Join` and several `%w` in one `fmt.Errorf`.** They are rare in the code this is for. The model extends to them: the tree has several branches, each guarded by its error not being nil, and since Go 1.20 both behave the same way. Until then several `%w` give a tree that is not known.
- **`errors.Unwrap`.**
- **A new error known to differ from a parameter or the result of a call.** It needs an allocation number for every error made, and a fact on every error read that its number lies below the allocation frontier.
- **Struct invariants that name an error variable**, which needs the keys of their spellings to travel with the invariant as they do with a contract.

### Integers

Built: every integer type, overflow obligations for arithmetic, negation, division, and conversion, and the named limits (`MaxInt` and friends) in annotations. Shifts and bitwise operators are expressed by arithmetic (`vego/bits.go`): a shift is a multiplication or division by a power of two, `x & y` is an unknown with the facts that hold of any two integers in two's complement plus exact ones for constant masks, and the other operators follow from it by identities such as `x | y = x + y - (x & y)`. Not built yet: bit operators in annotations, so that a function can say which bit it set; more about `x & y` than its bounds when neither operand is a constant mask (the XOR swap and `x&(x-1) == 0` are not proved); and automatic range facts for slice elements inside quantified annotations.

Decisions:

- **Overflow is an error for every integer type, including `int`.** Go wraps silently; verified code may not. Each arithmetic operation carries a proof obligation that its result fits the type, so program values always equal their mathematical values. The same goes for conversions to a narrower type, negation of the minimum value, and `MinInt / -1`. Code that wraps on purpose (hashes, checksums) cannot be verified and belongs in the trusted file.
- **Annotations keep mathematical integers.** `|A| + 1` in a contract never overflows.
- **A shift to the left must not lose bits**, for the same reason, and a shift count that may be negative is an error since Go panics on one.
- **Bits are facts about integers.** Everything about `&`, `|`, `^` and shifts is told to Z3 as facts about unknown integers, each of which is true of all integers in two's complement and tested against Go's operators in `bits_test.go`. Z3's bit-vector theory is not used: values stay mathematical integers throughout, and mixing them with bit-vectors would need a conversion at every operator. It is the way to the XOR swap and `x&(x-1) == 0` if those are wanted.

How the solver supports this: Z3's integers are unbounded, so bounds like 2^63 - 1 need nothing special; its nonlinear arithmetic covers `i*w + j < h*w` from `i < h` and `j < w`, and deeper facts are left to an `Assert`; built-in facts such as `|A| <= MaxInt` come from the verifier.

### Floats

Built as decided.

Decision: floats are opaque. The verifier tracks a `float32` or `float64` through the code but knows nothing about its value: arithmetic yields an unknown float, a comparison an unknown boolean, and a conversion to an integer an unknown integer of that type. Modelling floats as real numbers is ruled out as unsound. Exact IEEE reasoning is possible now that the prover is Z3, which has a floating-point theory, and is not built.

Consequences, accepted because the first target is services, CLIs, infrastructure, and data structures, where floats are incidental:

- No fact about a float value can be stated or proved.
- An integer computed from a float needs an explicit range check before it is used as an index.
- A loop controlled by a float cannot be proved to terminate, so its function goes in the trusted file.

Possible later: facts that are true of real floats, such as small integers converting exactly, added when a concrete need appears.

### Strings

Built: the basic tier and approximate ranging. A concatenation must be proved not to exceed `MaxAlloc`, the largest allocation of the platform, for the same reason as an `append`.

Decisions:

- **Basic tier.** A string is an immutable sequence of bytes: length, indexing, equality, literals, concatenation, substrings `s[i:j]`, and the copying conversions `[]byte(s)` and `string(b)`. Substrings are safe here, unlike sub-slices, because strings cannot be written to.
- **Unicode, approximately.** In `for i, r := range s`, `r` is some valid character and the next index is one to four bytes further. Exact UTF-8 decoding is not modelled.
- **Left until real code needs it.** Contracts about content (prefixes, the position `Index` returns) and string ordering.
- **Kept opaque.** Formatting, parsing, and pattern matching. `fmt.Sprintf` returns some string; `strconv.Atoi` returns some number when `err = nil`.

## Later

### Runtime checks for trusted contracts (gradual mode)

A trusted contract may be wrong in practice. The remedy is to check it while the program runs under `go test`: evaluate the `Requires` before the call and the `Ensures` after it, and fail loudly on a violation. The same mechanism covers the other direction, where unproved code calls a verified function and nobody has checked the `Requires`. This is the paper's gradual mode, applied where it pays off most.

Planned mechanism: `go build -toolexec`. The Go toolchain lets a program wrap each compiler invocation and rewrite source files before they are compiled, which is how compile-time OpenTelemetry instrumentation works. vego would use it to inject the checks during test builds only, so:

- the source tree is never modified and no generated files are checked in;
- checks can be added at call sites of external functions, which have no source in the project to edit;
- production builds carry no overhead.

Things to settle when this is built: which formulas are executable (bounded quantifiers are, quantifiers over all integers are not), the cost of checks inside loops, and how a violation is reported so it points at the contract and not at the injected code.

This is deliberately deferred. Nothing else on the roadmap depends on it.

### Effects: marking which functions touch the outside world

Worth investigating; nothing is decided. An effect system records, per function, whether it may interact with the outside world. Functions without the mark are guaranteed to depend only on their arguments.

How it could combine with the current design:

- Trusted entries would declare the effect, for example `effects: [io]` on `os.ReadFile`. The verifier would infer it for verified functions from what they call.
- The always-fails rule already has this shape: a contract may leave failure open only if the function calls something whose contract does. An explicit effect would state that directly instead of deriving it from contract shape, and would catch a trusted entry for a pure function that merely has a weak contract.
- Pure functions could be given stronger reasoning: the same arguments give the same result, and they could be called inside annotations.
- A contract could forbid effects, for example to prove that a function does no I/O.

A further step, deliberately not planned, is modelling the world's state as an invisible input so that contracts can say when I/O succeeds and relate one call to another.
